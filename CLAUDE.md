# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TheEstimator is a project-effort estimation tool: PERT three-point estimates (optimistic / likely / pessimistic) per work item, organised in an arbitrary-depth tree of groups and leaves, with versioned draft → submitted snapshots, audit trail, and comparison between versions. The German-language UI is intentional. **Domain source code is English, though** (phase-16, task-121): the German semantic parameter keys were Anglicised — `Tagessatz` → `dailyRate`, `Standardabweichungsfaktor` → `stdDevFactor`, `Vertriebszuschlag` → `salesSurcharge` (persisted rows migrated in `V11`; those keys became typed fields in task-138, see "Hardwired calculation inputs") — and domain comments/`InvariantResult` descriptors are English. The backend (`:backend:implementation`) is likewise English-only in source — identifiers, comments, and `io.quarkus.logging.Log` messages (phase-16, task-122) — with the customer's German Excel sheet/column labels centralised as external data in `ExcelGermanLabels` (in the `io.github.theestimator.service` package, alongside `ExcelImporter`/`ExcelExporter`); the German sample-data content in `testdata/TestDataSeeder.kt` is likewise intentional external fixture data. The German UI strings are being moved into per-user i18n catalogs (phase-16).

## Build & run

A single **Gradle** multi-project build drives every module. **Use `./gradlew`** (Gradle wrapper at the repo root — pins the Gradle version, downloads it on first run so contributors don't need a system `gradle`). The Kotlin plugin is unified at one version across `:domain` and `:backend:implementation` (it is a single shared artifact); compilation runs in-process (`kotlin.compiler.execution.strategy=in-process` in `gradle.properties`) to avoid stale Kotlin-daemon version clashes.

```
./gradlew build                            # full build, all tests (domain + backend + frontend)
./gradlew build -x test                    # build everything, skip tests
./gradlew staticAnalysis                   # ALL static analysis: detekt + frontend svelte-check & ESLint (informational, no Docker); also writes a consolidated build/reports/static-analysis/static-analysis.html
./gradlew detekt                           # Kotlin-only static analysis (detekt reports)
./gradlew :domain:build                    # domain (KMP) build + tests only
./gradlew :backend:implementation:test     # backend unit + @QuarkusTest (PostgreSQL via Dev Services — Docker required)
./gradlew :frontend:check                  # TS/Svelte type-check + ESLint
cd src/frontend && npm run test:e2e        # Playwright

./scripts/dev.sh                           # PostgreSQL (Dev Services) backend + Vite frontend, one command
#   → backend on :8090 (NOT 8080), Vite on :5173
./scripts/minikube-deploy.sh               # full PostgreSQL + Quarkus stack on minikube
```

Run one backend test class:
`./gradlew :backend:implementation:test --tests "io.github.theestimator.rest.EstimationVersionResourceIT"`

The local **dev backend listens on :8090**, not Quarkus' default 8080 (`%dev.quarkus.http.port`, task-137). 8080 is deliberately left free for `kubectl -n estimation port-forward svc/frontend 8080:80`: both can bind simultaneously (the port-forward takes `127.0.0.1`, Quarkus `0.0.0.0`), the loopback binding wins for `localhost`, and the Vite proxy plus the Playwright suite then silently reach the CLUSTER — which rejects `Authorization: Dev …` with `401` while both stacks look healthy. Do NOT move it back to 8080. The setting is profile-scoped on purpose: the generated OpenAPI `servers` block comes from the augmentation-time port, and prod augmentation must keep emitting 8080 so the committed `src/frontend/src/lib/api/openapi.json` does not churn. In-cluster ports (`k8s/base/backend/*`) stay 8080 — they are unrelated. All profiles use PostgreSQL 16 — there is no H2. Local dev (`dev` profile) and tests (`%test`) start a throwaway PostgreSQL container via Quarkus Dev Services, so **Docker must be running** for local backend runs and for the test suite; dev-minikube and prod use real PostgreSQL via Flyway migrations (`src/backend/implementation/src/main/resources/db/migration/V*.sql`).

## Architecture

A single Gradle build with these projects (`settings.gradle.kts`): `:domain`, `:domain:core`, `:domain:method-threepoint`, `:domain:method-bucketsampled`, `:backend:implementation`, `:backend:end2end`, `:frontend`.

The domain is **four** projects since task-143, so the estimation-method boundary is compiler-enforced rather than a convention: `:domain:core` (`src/domain/core`) holds the model, i18n, service and the method SPI + registry and depends on **no** method module; `:domain:method-threepoint` and `:domain:method-bucketsampled` each depend only on `:domain:core`; and `:domain` (`src/domain`) is the **aggregator** that depends on all three and is what `:backend:implementation` and `:frontend` consume. Package names are unchanged — only which project compiles them. **Every one of those dependencies must be `api(...)`, never `implementation(...)`**: the backend depends on the aggregator and imports `io.github.theestimator.model.*` in ~13 files, and `implementation` dependencies do not reach a consumer's compile classpath, so downgrading one breaks the backend build wholesale. A cross-method import is now an "Unresolved reference" compile error, not merely a review comment.

- **`src/domain`** (`:domain`) — Kotlin Multiplatform (JVM + JS). Compiles to a JVM jar consumed by the backend via `project(":domain")` and to TypeScript + JS for the frontend (Gradle tasks `compileKotlinJvm`, `jvmTest`, `packageTypescript`); the packaged TS zip is exposed as a consumable `typescriptDist` configuration that `:frontend` unpacks into `src/lib/domain`. **Holds all business logic** — PERT calculation, accumulation, the tree-shape domain model. The backend and frontend MUST NOT reimplement domain rules; they call into it.
- **`src/backend/implementation`** (`:backend:implementation`) — Quarkus 3 (Java 21, Kotlin) via the `io.quarkus` Gradle plugin, Hibernate ORM Panache, Flyway, Jib for container images. REST endpoints under `/api/`.
- **`src/frontend`** — SvelteKit 5 (runes) + TypeScript + Tailwind 4, Vite, adapter-static (SPA). Talks to the backend via `apiFetch` (`$lib/api/fetch.ts`), a thin `fetch` wrapper that attaches the active auth provider's `Authorization` header; request/response types are generated from the backend OpenAPI via openapi-typescript into `$lib/api/schema.d.ts`. Raw `fetch(...)` is banned by ESLint (`no-restricted-syntax`) in favour of `apiFetch` (task-090). **File downloads are no exception**: a plain `<a href="/api/…" download>` is banned too, because browser navigation carries no `Authorization` header — the strict dev module then answers `401` and the browser silently SAVES THAT JSON ERROR BODY as the "export" file (the xlsx/csv export menu shipped that way and produced no spreadsheet at all). Every download goes `apiFetch` → `assertOk` → `res.blob()` → the shared `downloadResponse(blob, contentDisposition, fallbackName)` in `$lib/api/download.ts`, which reads the filename out of the `Content-Disposition` header and clicks a temporary object-URL anchor; both the version editor's xlsx/csv export and the estimation detail page's Merlin export use it, and `e2e/export.test.ts` pins that the downloaded bytes are a real zip/CSV rather than a JSON error body. Per-method editor UIs are pluggable: `$lib/methods/registry.ts` maps each `EstimationMethod` to a lazy `import()` of `$lib/methods/<method>/EditorModule.svelte`; the version editor route reads the estimation's `method` and renders the resolved module as a dynamic component, while keeping autosave + undo/redo on the route (the module is a pure `$bindable` view). `registry.ts` also exports `availableMethods` (derived from the registered modules + a `methodLabels` map) which drives the method picker in `CreateEstimationDialog.svelte` (task-116) — registering a method there implies full-stack support. PERT lives in `methods/pert/`; the bucket + sampled editor lives in `methods/bucketSampled/` (task-104): `EditorModule.svelte` renders the shared panels plus a `BucketPanel.svelte` (add/rename/delete/drag-reorder buckets, `svelte-dnd-action`) and a `TreeTable` of bucketed leaves (bucket picker → `bucketId`, sample toggle → `isSample`, a three-point editor shown only on sample rows, and a read-only derived `mean` column for non-sample rows). Since task-132 that editor offers **two views** over the same `roots`, toggled by a segmented control (the choice persists in `localStorage` under `estimator.bucketView`; default `bucket`). They are **two projections of one model**, and their drag-and-drop meanings are deliberately disjoint: the **bucket view** renders a `$derived` synthetic tree — one row per bucket in `position` order plus a trailing `bucket:unassigned` row (which also collects leaves stranded by a deleted bucket) whose children are the *flattened* leaves of the whole tree; that unassigned row is a rescue **source only** — a drop *into* it is deliberately ignored, because the backend rejects a `BUCKETED` leaf with a null `bucketId` (`400`), so accepting it would only yield a failing autosave. A drop onto a real bucket changes **only** `bucketId` (via `onChildrenChange`, never moving anything in the real tree; ordering inside a bucket is **not persisted**, so a same-bucket reorder is a deliberate no-op). The **hierarchy view** is the real nested-group tree with `+ group` / `+ item` / `✕` row actions, where a drop restructures the tree and never touches `bucketId`. Bucket estimations legitimately contain `GROUP` nodes — the Merlin importer (task-131) creates exactly that shape — which the old flat editor could not display at all. Synthetic bucket rows are **not** domain groups: they carry a synthetic `logicalId` (`bucket:<id>`) only to satisfy `TreeTable.getId`, and their numbers are a display-only **sum** of their leaves' already-computed `calcMap` entries; all bucket math stays in the domain's `BucketMethodModule`. The per-row bucket `<select>` remains in both views so re-bucketing stays keyboard-reachable. Since task-134 the bucket view opens with all **bucket rows collapsed** — expressed as `TreeTable.defaultCollapsed={isBucketRow}` (its first consumer), so every bucket is visible at once and a cross-bucket drag is a short movement. `defaultCollapsed` is a **rule, not a seed**: it is consulted for every row the user has not toggled, so a bucket added after mount starts collapsed too (it was seeded once into local state before, which both made a later-added bucket render expanded and tripped Svelte's `state_referenced_locally` warning — do not go back to copying the prop into `$state`). That collapse state is transient: it is not persisted (unlike the view choice in `localStorage`), and toggling to the hierarchy view and back remounts the table, dropping the user's overrides so the rule re-collapses the rows. The hierarchy view stays fully expanded — there the nesting is the information. The route owns a `currentBuckets` `$state` (read from the estimation-detail `buckets`, seeded XS/S/M/L/XL for a fresh draft) and PUTs it as `DraftUpdateDto.buckets`. The chosen estimation method is surfaced in the project-detail estimations table, the estimation-detail header, and the version editor header via `$lib/methods/labels.ts::formatMethodLabel` (task-118).

### Domain model: trees, not flat groups

The estimation hierarchy is an **arbitrary-depth tree**. Sealed hierarchy in `src/domain/src/main/kotlin/io/github/theestimator/model/`:

```
EstimationNode (sealed)
├── EstimationGroup           — interior node; title + List<EstimationNode> children;
│                               accumulates mean/variance/offerPT/cost/offerPrice
│                               over its subtree via `get() = children.sumOf { … }`
└── EstimationItem (sealed)   — leaf; carries the raw PERT values
    ├── FixedEstimationItem
    └── TimeRelativeEstimationItem    — mean scales by phase.durationWeeks
```

`EstimationVersion.roots: List<EstimationNode>` is the tree root. `EstimationVersion.calculate()` flattens leaves, computes the risk factor + driver factor + daily rate, builds `CalculationParameters`, then maps the tree via `withCalculationParameters(...)`. Groups derive their numbers from children — never store accumulated values on `EstimationGroup`.

A `leaves()` extension on `EstimationNode` flat-walks the tree and returns the leaf items.

#### Hardwired calculation inputs

The three calculation inputs — **`dailyRate`, `stdDevFactor`, `salesSurcharge`** — are typed `Double` **fields**, not generic name/value rows (task-138). They used to be a `List<EstimationParameter>` that `EstimationVersion.calculate()` looked up by the literal English strings `"dailyRate"`/`"stdDevFactor"`/`"salesSurcharge"`; because the GUI let the user edit the parameter NAME, a rename made the lookup miss and the estimate **silently fell back to the default** — a wrong number with no error anywhere. Typed fields make that unrepresentable, and they are what let the parameter panel be internationalised (a label is now an i18n key, not the lookup key).

So: **do not reintroduce a generic parameter collection.** `EstimationParameter`, `DraftEstimationParameter` and `SubmittedEstimationParameter` are deleted; the `draft_estimation_parameters` / `submitted_estimation_parameters` tables were folded into `daily_rate` / `std_dev_factor` / `sales_surcharge` columns on both version tables by `V16` (which back-fills each row from its old parameter rows before dropping them, defaulting anything absent). `DraftUpdateDto` carries the three as flat optional fields (`dailyRate?`, …) applied by direct assignment in `DraftUpdateApplier`, and `VersionComparisonService` still emits `ParameterChangeDto` — its `name` is now the fixed FIELD name, which the compare page maps straight onto the `panel.parameters.<name>` i18n label.

Their default values live in **one** place, the `@JsExport`ed `EstimationDefaults` object in the domain (`io.github.theestimator.model`): the domain constructor defaults, the JPA column defaults on `DraftEstimationVersion`/`SubmittedEstimationVersion`, and the frontend `ParametersPanel`'s "use defaults" button all read it (the frontend via `EstimationDefaults.getInstance().DAILY_RATE`). Do not re-hardcode `800.0` / `2.0` / `0.1` anywhere.

#### Pluggable estimation methods (SPI)

Estimation methods are pluggable behind a domain SPI in `io.github.theestimator.method` (phase-15, planned in task-096). `EstimationMethod` is a `@JsExport` enum (`THREE_POINT_PERT`, `BUCKET_SAMPLED_PERT`); `EstimationMethodModule` is the interface each method implements — it supplies the per-leaf `calculate(item, params)` (mirroring `EstimationItem.withCalculationParameters`), a batch `calculateAll(items, params)` hook (default maps `calculate` per leaf; overridden by methods that need per-bucket context), plus the export `exportRow` / `exportColumnHeaders` shaping; and `EstimationMethodRegistry` is a singleton `object` mapping enum → module (`register` / `get` / `require` / `all`, where `require` throws for an unregistered method). **One Gradle MODULE per method** (task-143, was "one Kotlin package per method") — each concrete method lives in its own `io.github.theestimator.method.<method>` package **compiled by its own Gradle project**, so cross-method references are a compile error rather than a convention violation; all interaction goes through the SPI. Only the enum is `@JsExport`ed; the interface and registry stay domain-internal.

**The registry does NOT self-populate.** It used to install the standard methods from its own `init {}`, but that required `:domain:core` to name the concrete modules, which is exactly the cycle the module split forbids. Installation moved to `io.github.theestimator.StandardMethods.installAll()` in the aggregator `:domain`, and each runtime bootstraps explicitly: the **backend** via `MethodRegistryBootstrap` (`@Observes StartupEvent`, mirroring `AuthProviderGuard`), **Kotlin/JS** via `DomainFactory.createVersion` (so `adapter.ts` needs no call), and **tests** by calling `installAll()` directly — or, inside a method module whose tests cannot see the aggregator, by registering their own module. Forgetting it surfaces immediately as `IllegalStateException: No estimation method module registered for …`. Three core→method references had to be inverted to make this possible: `EstimationItem` now declares `abstract val method` (so `EstimationVersion.calculate()` no longer sniffs leaf types) and `abstract val nodeTypeLabel` plus `diffFields(): List<LeafDiffField>` (so `DiffSummary` no longer branches on `BucketedEstimationItem` / `TimeRelativeEstimationItem`). `diffFields()` is `@JsExport.Ignore`d — it is a domain-internal hook, and it cannot be `internal` because its overriders live in sibling Gradle modules. For the same module-scoping reason `newId()` and `EstimationMethodRegistry.clear()` are now public rather than `internal`.

**Kotlin/JS granularity is pinned to `whole-program`** (`kotlin.js.ir.output.granularity` in `gradle.properties`). The default `per-module` emits one `.mjs` per Gradle project, which split the runtime exports across `domain.mjs` / `the-estimator-domain-core.mjs` / … while Kotlin still wrote **all** TypeScript declarations into the single `domain.d.mts`. The frontend then type-checked fine and failed at bundle time with `"EffortDriver" is not exported by "src/lib/domain/domain.mjs"`. `whole-program` merges everything back into one `domain.mjs`, so the frontend keeps its single import site and `src/frontend/src/` needed no change at all; total shipped JS is unchanged (~338 KB, the stdlib is now inlined rather than a sibling file). Do not switch this back. Each `EstimationMethodModule` also carries a `description: String` — a human-readable English description that the backend serialises verbatim as `EstimationDetailDto.methodDescription` and the frontend renders in `MethodDetailPopover.svelte` when the user clicks the method badge (task-119).

`EstimationMethodSessionSupport` is a **second, sibling SPI** in the same package (task-105) — collaborative-session behaviour, deliberately NOT nested inside `EstimationMethodModule` (session support is inherently multi-estimator, so folding the two together would over-generalise both). It exposes `method` + `reduce(votes: List<SessionVoteInput>): SessionReduction`, and the same registry carries it via `registerSessionSupport` / `getSession` / `requireSession` (throwing, like `require`); `installStandardMethods()` registers `ThreePointSessionSupport` alongside the modules, and the test-only `clear()` empties both maps. Like `EstimationMethodModule`, it is domain-internal — not `@JsExport`ed. `ThreePointSessionSupport.reduce` **delegates** to `VoteAggregation.aggregate` rather than rehoming the math (the frontend bridge and `VoteAggregationTest` still reference it directly), so the SPI is a dispatch seam.

`SessionVoteInput` / `SessionReduction` (task-142) are the method-neutral marker interfaces that signature is built on; each method contributes its own subtypes **from its own package** (PERT: `PertVoteInput` / `PertReduction` in `…method.threepoint`). Two decisions there are deliberate and load-bearing. **They are not type parameters** (`EstimationMethodSessionSupport<I, R>`): the registry keeps every support in one `Map<EstimationMethod, EstimationMethodSessionSupport>`, so a generic interface erases to `*` in that map and `requireSession(...)` would return a star-projected type, forcing an unchecked cast at every call site. **They are also not `sealed`**, which would otherwise be the natural way to get an exhaustive `when`: Kotlin requires a sealed type's direct subtypes to live in the *same package*, which is mutually exclusive with the one-package-per-method rule above — declaring them in a method package fails to compile outright ("A class can only extend a sealed class or interface declared in the same package"). Exhaustiveness is replaced by the contract that `reduce` must `error(…)` on an input subtype it does not handle. `EstimatorVote` / `VoteAggregate` are **wrapped** by the PERT subtypes rather than implementing the markers directly, because they are `@JsExport`ed and reach the frontend through `DomainFactory.aggregateVotes` — giving them a domain-internal supertype would perturb the generated `domain.d.mts` surface for no gain.

Method #1 is three-point PERT (task-098): `ThreePointMethodModule` in `io.github.theestimator.method.threepoint` wraps the existing per-leaf PERT calc and owns the PERT export column shape (`exportColumnHeaders` = `Min/Expected/Max`, in English); both the CSV and Excel exporters source their input-column headers from it, so the module is the single source of the PERT column shape. **`EstimationItem` is `abstract` (task-113), so each method owns its leaf type in its own package.** `EstimationNode` stays `sealed` (its direct subclasses `EstimationGroup` + `EstimationItem` remain in `io.github.theestimator.model`, keeping `EstimationNode.leaves()` exhaustive), but the concrete leaf types live under their method: PERT's `FixedEstimationItem` / `TimeRelativeEstimationItem` are in `io.github.theestimator.method.threepoint`, and task-102's `BucketedEstimationItem` lands in `io.github.theestimator.method.bucketsampled`. Because `EstimationItem` is no longer sealed, the domain→submitted `when` in `EstimationVersionService` has an explicit `else -> error(…)` for unhandled leaf types. Registry-driven export dispatch by `estimation.method` lands in task-107.

Method #2 is bucket + sampled PERT (task-102): `BucketMethodModule` / `BucketedEstimationItem` in `io.github.theestimator.method.bucketsampled`. A `BucketedEstimationItem` belongs to a bucket (`bucketId`) and is either a **sample** — carrying its own `optimistic`/`likely`/`pessimistic` three-point estimate, from which `mean`/`variance`/`offerPT` derive by the usual PERT formula — or a **non-sample**, whose neutral values are the per-bucket average of that bucket's samples. Because a single leaf can't see its bucket siblings, the module overrides the SPI's `calculateAll(items, params)`: `computeBucketAverages(items, params)` averages each bucket's samples once, then `withCalculatedFromBucket(mean, variance, offerPT)` stamps those onto the non-sample leaves (`cost`/`offerPrice` derive from `offerPT` via the inherited getters). `EstimationVersion.calculate()` dispatches through this batch hook — it detects the method from the leaf types (any `BucketedEstimationItem` → `BUCKET_SAMPLED_PERT`, else `THREE_POINT_PERT`), runs `calculateAll` over the flat leaves, and substitutes the calculated leaves back into the tree by `logicalId` before the group accumulation; the PERT path stays byte-identical because its default `calculateAll` is per-leaf. This adds a `model → method` reference (`EstimationVersion` → `EstimationMethodRegistry`), which is acceptable (consistent with `DomainFactory`) and is NOT a method-to-method reference. Backend persistence for buckets lands in task-103; the frontend editor in task-104.

### Persistence shape

The `estimations` table carries a method column (`method`, `VARCHAR(255)`, V9 migration; JPA `@Enumerated(STRING) var method: EstimationMethod`) — the estimation's `EstimationMethod`, chosen at creation and **immutable** (there is no estimation-update endpoint, so nothing mutates it after create). Every version of one estimation shares its method.

Single self-referential table per side, JPA `SINGLE_TABLE` inheritance with a `node_type` discriminator (`GROUP` | `FIXED` | `TIME_RELATIVE` | `BUCKETED`). Children ordered by an integer `position` column (`@OrderColumn`). The version's `roots` use `@SQLRestriction("parent_id IS NULL")` to pick out the top-level rows.

**Buckets** (bucket + sampled method, V10 migration): the `estimation_buckets` table (`id`, `estimation_id` FK `ON DELETE CASCADE`, `position`, `label`, `UNIQUE(estimation_id, position)`) is owned by the `Estimation` (`Estimation.buckets`, ordered by `position`) and shared across its draft + submitted versions. The bucket `id` is **client-assigned** (like a node's `logicalId`, not `@GeneratedValue`) so a single draft PUT can send new buckets together with the leaves that reference them. Both node tables gain a nullable `bucket_id` (FK `ON DELETE RESTRICT`) and `is_sample` column; the `BUCKETED` `@DiscriminatorValue` subclasses (`DraftBucketedItemNode` / `SubmittedBucketedItemNode`) carry the `@ManyToOne bucket` + `isSample` and **reuse the existing `min_effort`/`expected_effort`/`max_effort` columns** for a sample's optimistic/likely/pessimistic triple (non-samples leave them NULL and inherit the bucket average via `calculate()`). `DraftUpdateApplier.applyBuckets` upserts `estimation.buckets` by id (not clear-and-rebuild, since nodes FK-reference them) and runs before `applyRoots`; a `BUCKETED` leaf is accepted only when `estimation.method == BUCKET_SAMPLED_PERT` (else `400` + `Log.warn`) and its `bucketId` must resolve to an existing bucket. `DraftSnapshotMapper` captures the buckets so undo/redo round-trips them; `EstimationDetailDto.buckets` exposes them on the wire. **Reordering buckets swaps `position` values**, which `applyBuckets` writes as row-by-row UPDATEs — and `UNIQUE(estimation_id, position)` is evaluated by PostgreSQL after EVERY statement, so the transient mid-swap duplicate aborted the transaction ("could not be saved", reorder lost). Two things keep that correct and must not be undone: `applyBuckets` first parks every existing bucket on a temporary NEGATIVE position and flushes, so no final position can collide with a stale one; and `V15` makes the constraint `DEFERRABLE INITIALLY DEFERRED` in the Flyway-managed schemas. The constraint is ALSO declared on the `EstimationBucket` entity — deliberately, for **dev/prod schema parity**: `%test`/`%dev` build the schema from Hibernate (`drop-and-create`, Flyway off) while prod/dev-minikube use Flyway, so without the entity-level declaration the local schema had no such constraint at all and this bug was literally unreproducible outside the cluster. When adding a constraint in a migration, add it to the entity too, or it will not exist where you test.

- **Draft** side: `draft_estimation_nodes` (V6 migration); JPA entity `DraftEstimationNode` with three `@DiscriminatorValue` subclasses (`DraftGroupNode`, `DraftFixedItemNode`, `DraftTimeRelativeItemNode`). Mutable, edited via the REST PUT endpoint.
- **Submitted** side: `submitted_estimation_nodes` (V7 migration); mirrors the draft shape with `SubmittedEstimationNode` + `SubmittedGroupNode`/`SubmittedFixedItemNode`/`SubmittedTimeRelativeItemNode`/`SubmittedBucketedItemNode`. **Submitted entities are immutable snapshots** that store the calculated values directly on every row (mean, offerPT, cost, …); group rows store accumulated values for their subtree. `BUCKETED` rows additionally persist the raw method-specific input (`bucket_id`, `is_sample`, and the sample triple in `min/expected/max`) so a detail view or export can reproduce the input. The backend never recomputes on read.

**Undo log** (V8 migration): `draft_estimation_versions` gains a `revision` counter plus `last_modified_by` / `last_modified_at` audit columns, and a new append-only `draft_mutation_log` table records one row per applied `DraftMutation` (`DraftMutationLogEntry`): monotonic `sequence_number` per draft, `revision_before`/`revision_after`, `kind` discriminator, `payload` + `inverse_payload` (`jsonb`, mapped `String` via `@JdbcTypeCode(SqlTypes.JSON)`), and an `ACTIVE`/`UNDONE` status. Finders live on `DraftMutationLogRepository`. `UndoService` records one entry per draft-changing `updateDraft` (skipping no-op PUTs via `EstimationVersion.diff`), and provides per-user `undoLastForUser` / `redoLastForUser` (restoring the stored `DraftUpdateDto` snapshot via `DraftUpdateApplier`) plus `historyFor`; a cross-user change on top of the target raises `UndoConflictException`. Snapshots are stored as `StoredMutation(kind, before, after)` DTO JSON (`DraftMutationJackson`), not raw domain types. Submitting a draft cascade-deletes its log.

**Collaborative estimation sessions** (phase-11, V13 migration): four tables under `io.github.theestimator.domain.session` (all JPA `BaseEntity` — uuid `id` + `created_at`/`updated_at`). `estimation_sessions` (`EstimationSession`: `estimation_id` FK, `title`, `moderator_subject_id`, `status`, `current_item_index`, `current_phase`, `finalized_at`, and `moderator_estimates` boolean default true — V14, task-129: whether the moderator also votes) — the coarse lifecycle is `SessionStatus` (`CREATED`/`RUNNING`/`FINALIZED`/`CANCELLED`); per-item progress is tracked by `session_items.status` + `current_item_index`/`current_phase`. `session_items` (`SessionItem`: `node_logical_id` — a **soft** reference to a draft leaf's `logical_id`, not an FK — `position`, `status` = `SessionItemStatus`, `discussion_notes`, and the `final_min/expected/max_effort` write-back triple; `UNIQUE(session_id, node_logical_id)`). `session_participants` (`SessionParticipant`: `subject_id`, `display_name`, `participant_role` = `ParticipantRole`, `agreed`; join time is `created_at`; `UNIQUE(session_id, subject_id)`). `session_votes` (`SessionVote`: `session_item_id` FK, `participant_subject_id`, `phase` = `SessionPhase`, the `min/expected/max_effort` triple; submission time is `created_at`; `UNIQUE(session_item_id, participant_subject_id, phase)` so a re-vote in a phase overwrites). All FKs cascade-delete from the session. The vote/finalize columns are the **THREE_POINT_PERT** shape; the bucket+sampled method votes on bucket assignments and extends storage separately (task-106). Repositories: `EstimationSessionRepository` (`findByEstimationId`, `findParticipant`) and `SessionVoteRepository` (`findBySession`, `findByItemAndPhase`). REST/WebSocket wiring lands in task-064/065.

Use `@SQLRestriction`, not the deprecated `@Where`, for filtered collections.

### Frontend ↔ domain bridge (`adapter.ts`)

`src/frontend/src/lib/adapter.ts` computes the local calc map by calling into the Kotlin/JS-compiled domain (`createVersion(...).calculate()`) and then walking the result tree recursively. Its entry point is `computeEstimation(roots, params, drivers, phases, additionalCosts)` (task-139, formerly `computeCalcMap`), which returns **`{ calcMap, totals }`** from a SINGLE build+`calculate()` — the per-node map and the whole-estimation totals come off one domain round-trip, so an edit does not recompute the version twice per keystroke. The `totals` half is the domain reducer `EstimationVersion.totals()`; see the summary-panel note below. Both the wire DTOs (`EstimationVersionDto.roots`, `DraftUpdateDto.roots`) and the Kotlin/JS factories (`createVersion(roots: Array<EstimationNode>)`, `createGroup(children: Array<EstimationNode>) → EstimationGroup`, `createFixedItem`, `createTimeRelativeItem`, and `createBucketedItem(description, bucketId, isSample, optimistic, likely, pessimistic, logicalId)` for the bucket method — task-104) speak the canonical tree shape — no legacy `itemGroups` field anywhere. The `adapter.ts` calc map carries `mean` alongside `offerPT`/`cost`/`offerPrice` so the bucket editor can show each non-sample leaf's domain-derived bucket mean. If you see a stale `.d.mts` (TypeScript picks `.d.mts` for `.mjs` imports), force a full rebuild: `./gradlew :domain:clean :frontend:clean :frontend:check`. (Kotlin 2.3.x emits `domain.d.mts` directly; `prepareTypescriptArtifacts` copies it through.)

### Kotlin/JS gotcha — super-property recursion

`super.<computed property>` infinite-loops on Kotlin/JS but works on JVM (see the comment in `TimeRelativeEstimationItem.kt`). When overriding a getter that needs the parent's formula, **inline the formula**; never call `super.mean` / `super.variance`. The build will compile and the JVM tests will pass, but the frontend will throw "Maximum call stack size exceeded" at runtime.

### Kotlin/JS gotcha — secondary constructors

`@JsExport`-ed classes need `@JsName("…")` on secondary constructors (Kotlin/JS rejects them otherwise). Two `data class` constructors whose value types erase to the same JVM signature (e.g. two `List<X>`) cause a platform declaration clash — differentiate by arity, not by type alone.

### Reproducible Jib backend image

`src/backend/implementation/gradle.properties` configures Jib for byte-deterministic images. **Both** `quarkus.jib.use-current-timestamp` and `quarkus.jib.use-current-timestamp-file-modification` must be `false`. Setting only one yields non-reproducible builds.

## Conventions

### Single source of truth — domain logic

Anything you'd want to call "business logic" (PERT, accumulation, risk surcharge, cost rules, version equality, invariants) lives in `src/domain/`. Do not duplicate it in backend services or frontend stores. The backend and frontend exist to map persisted state ↔ domain and to render / edit; they do not re-derive numbers.

### Backend run-of-the-mill patterns

- Domain → entity mapping in `…/service/DraftVersionMapper.kt`; entity → DTO mapping in `…/rest/dto/EstimationVersionMapper.kt`; entity → `DraftUpdateDto` snapshot in `…/service/DraftSnapshotMapper.kt` (`DraftEstimationVersion.toUpdateDto()`).
- Writing a `DraftUpdateDto` into a draft entity is centralised in `…/service/DraftUpdateApplier.kt` (`apply(draft, update)`) — the `dto.field?.let { … list.clear(); list.add(…) }` clear-and-rebuild shape (rather than diffing). Both the REST PUT `updateDraft` and the Undo service call it; `toUpdateDto()` is its inverse (capture), so `apply(draft, draft.toUpdateDto())` is a no-op on state.
- Repositories are Panache (`PanacheRepository<T>`). Add finders as extension methods on the repository class.

### Frontend — error surfacing rule

Every `try`/`catch` MUST surface failure to the user via the shared `ErrorBanner` component (`src/frontend/src/lib/components/ErrorBanner.svelte`). A `catch` that returns a fallback while only logging to `console.error` is **not** acceptable — that is the bug pattern that hid the Kotlin/JS stack-overflow as blank `—` cells in the grid. The single seam that turns a failed HTTP `Response` into a user-facing message is `src/frontend/src/lib/api/errors.ts` (`assertOk(res, fallback)` / `messageForStatus`, task-093) — it prefers the backend error body's `message`, else a status-specific default (401/403 → fixed authorization strings). Call sites do `await assertOk(res, '<fallback>')` after `apiFetch`, then keep their `try`/`catch` → `log.error(...)` + `bannerMessage`; do NOT scatter raw `if (!res.ok) throw new Error('…')` status checks across pages. The request seam `apiFetch` itself **throws** `Authentication failed: <reason>` (with the original error as `cause`) when the auth provider cannot produce a token (e.g. MSAL silent-token acquisition fails after an Entra app-registration change) — it does NOT fall through and send an anonymous request that would only 401 with a misleading "session expired". A `null` header (not signed in) is not a failure: the request goes out anonymous and the backend 401 drives the sign-in message. A genuine **connection loss** (task-136) — `apiFetch`'s `fetch` rejecting, its ~10s `AbortController` timeout firing, or a `502/503/504` — is escalated (not to the banner) via the global `ConnectionStore` (`$lib/stores/connection.svelte.ts`, `connection.reportLost(...)`), which **blocks the whole app** with `ConnectionLostDialog` (mounted once in the root `+layout.svelte`, overlays every route). The block stays until a heartbeat — the unauthenticated `GET /api/ping` (`PingResource`, `@PermitAll`), polled every ~3s — answers AND the user acknowledges; acknowledging does a **full page reload** (`window.location.reload()`, not `invalidateAll()`) so the unsaved (lost) edit is discarded rather than silently re-saved by a later autosave. Ordinary 4xx/5xx business errors keep the non-blocking `ErrorBanner` path; a caller-initiated `AbortController` cancel is not treated as a connection loss.

### Frontend — `$bindable` two-way binding (editor components)

The version editor lets Svelte own state end-to-end. The page (`routes/estimations/[id]/versions/[versionNumber]/+page.svelte`) holds one source-of-truth `$state` per collection (`currentParameters`, `currentDrivers`, `currentPhases`, `currentAdditionalCosts`, `currentRoots`, `currentNotes`), normalised once in `loadVersion()` (roots via `normalizeRoots` from `$lib/estimationNodes`). It passes each down with `bind:` to the editor children — the four sibling panels (`ParametersPanel`, `EffortDriversPanel`, `PhasesPanel`, `AdditionalCostsPanel`) and `EstimationGrid` — which declare the data prop as `$bindable()` and **mutate it directly** (`push`/`splice`/field assignment, or reassign for wholesale replacement). There is no local snapshot, no `notify()`, and no `onchange` callback; Svelte propagates child mutations back to the page. Autosave is a single guarded `$effect` in the page: it deep-reads the editable state via `$state.snapshot(...)`, compares against a `lastSavedSnapshot` baseline set at load, and debounces a PUT only on an actual edit to a draft (never on load/reload). Do NOT reintroduce the old "snapshot prop into local `$state` + onchange" pattern. (`TreeTable`'s expand/collapse is the one exception that stays deliberately local — it is private UI state the page does not own. It holds only the rows the user has EXPLICITLY toggled (`expandedOverrides`), falling through to the caller's `defaultCollapsed(node)` rule for the rest — a live read, not a copy of the prop into `$state`.)

### Frontend — whole-estimation totals (`EstimationSummaryPanel`)

The version editor route renders `src/frontend/src/lib/components/EstimationSummaryPanel.svelte` **above** the method module (task-139), so every method shows one total for the whole estimate — the bucket+sampled editor aggregates only per bucket and previously had no estimate-wide number at all. The panel is on the ROUTE, not in a method module, so the two methods cannot drift; it renders for drafts and submitted versions alike and is deliberately **not** `position: sticky` (the editors below it are `svelte-dnd-action` drop zones whose geometry the library measures at drag start).

The figures are **computed by the domain**, never summed in Svelte: `EstimationTotals` + `EstimationVersion.totals()` in `src/domain/.../model/EstimationTotals.kt`. `totals()` is a **member** function, not an extension — `@JsExport` does not export extension functions, so an extension would compile, pass `:domain:build`, and then be missing from `domain.d.mts`. It must be called on the result of `calculate()` (a leaf's `cost`/`offerPrice` derive from the `CalculationParameters` that `calculate()` stamps on), and it reads `offerPT` off the already-computed `totalEffort` rather than re-summing. `totalOfferPrice` follows the customer's canonical formula — `(developmentCost + additionalOneTime + additionalRecurring) × (1 + salesSurcharge)`, the one `ExcelExporter.writePhases` applies per phase — while the separate `developmentOfferPrice` is the tree's own price EXCLUDING additional costs, which is what a column of per-leaf offer prices sums to. A RECURRING additional cost with a null phase contributes 0 and is counted in `recurringWithoutPhase`, which the panel surfaces as a warning line rather than silently absorbing (the task-138 lesson).

`EstimationGrid`'s footer reads those same totals. It used to reduce `Array.from(calcMap.values())`, but that map holds an entry for **every node including GROUPs** and a group accumulates its whole subtree — so the PERT footer **double-counted every grouped estimation**. Its `min`/`expected`/`max` sums stay leaf-based via `allLeaves(roots)` (those were always correct). `e2e/summary-panel.test.ts` pins both halves.

### Frontend — undo/redo store (`UndoStore`)

Persistent undo/redo (task-076) is a thin client over the backend endpoints, wired into the version editor page. `src/frontend/src/lib/stores/undo.svelte.ts` exports the `UndoStore` runes class (`history`/`loading`/`conflict`/`error` `$state`, `canUndo`/`canRedo` `$derived`, and `refresh`/`undo`/`redo`/`clearConflict`). It owns **only** the mutation-log view — NOT the draft state: after a successful `undo`/`redo` it calls the owner-supplied `onResult(version)` hook, and the page replaces its draft `$state` through the same `applyVersionData` normalize path used on load (which also resets the autosave baseline, so re-hydrating from an undo never triggers a spurious PUT). The page calls `store.refresh()` after the initial draft load and after every successful autosave PUT, and mirrors `store.error` into its existing `bannerMessage`/`ErrorBanner`. A 409 is parsed into `conflict` (no throw). `src/frontend/src/lib/stores/undoKeyboard.svelte.ts` exports `installUndoShortcuts(store)` (Ctrl/Cmd+Z = undo, Ctrl/Cmd+Shift+Z / Ctrl+Y = redo), installed via an `$effect`; it defers to native input undo unless the target sits inside the grid's `data-undo-aware="true"` surface (set on `EstimationGrid`'s container). All HTTP goes through `apiFetch`; DTOs are the **generated** `components['schemas']` types from `$lib/api/schema` — this store is the first consumer of the generated `schema.d.ts` (existing components still use the hand-written `$lib/api/types.ts`). The visible UI (task-077) lives on the version editor page: Rückgängig/Wiederholen toolbar buttons (disabled via `canUndo`/`canRedo`, tooltips drawn from `history`), a collapsible `UndoHistoryPanel` rendered as a section directly under the toolbar (above the version title, task-109 — it used to sit below the editor grid, which put it off-screen and needed a `scrollIntoView` workaround), and a `UndoConflictDialog` shown whenever `conflict` is non-null (its "Aktuellen Stand neu laden" action re-runs the page's `loadVersion` + `refresh` + `clearConflict`; 409s go to this dialog, never to `ErrorBanner`).

### Frontend — generic `TreeTable` component

`src/frontend/src/lib/components/treetable/TreeTable.svelte` is a domain-agnostic, OmniOutliner-style tree-table component generic over a node type `T`. Callers supply `getId` / `getChildren` + a column array whose `cell` snippets render per-row content (branching on the node's data discriminator to draw editors on leaves and aggregates on group rows). The component owns indent guide lines, expand/collapse, nested per-group `svelte-dnd-action` dndzones, cycle protection (deep-clone snapshot + microtask-deferred structural-anomaly check: duplicate IDs OR lost IDs), and the header / optional footer / optional per-row actions slot. The zones use `useCursorForDetection`, so a children zone with **no** children must keep a `min-h-8`: an empty zone otherwise collapses to 0 px and can never be hovered, which silently made an empty group — and every freshly created (hence empty) bucket in the bucket view — impossible to drop into. A group's children zone is also rendered **when the row is collapsed** (task-134), because `svelte-dnd-action` captures its drop zones **at drag start** — `watchDraggedElement` instruments exactly the zones registered at that moment — so a zone that first appears mid-drag can never receive the drop. (That is why "spring-loading" a collapsed row on hover was tried, measured and rejected.) The collapsed row's descendants therefore stay in the DOM and are collapsed visually instead, via `h-0 overflow-hidden invisible` on the row wrapper — `visibility: hidden` rather than `display: none` on purpose: it keeps a layout box for the library's geometry while removing the subtree from the tab order. Because `items` and the DOM children stay one-to-one, `applyChildren` keeps its replace semantics and the cycle protection is unchanged. A collapsed zone claims its `min-h-8` strip only while a drag is in flight (`dragActive`, derived from the existing `draggedSubtreeIds`). The `roots` prop is `$bindable` so callers can run imperative add/delete mutations that the component reflects immediately. Optional `rowAttrs` and `childrenZoneAttrs` hooks let callers attach extra attributes (e.g. legacy testids, per-group aria-labels) to outer row wrappers and to children dndzones. Types live in `treetable/types.ts`. **Production consumer**: `src/frontend/src/lib/components/EstimationGrid.svelte` (the estimation editor — composes TreeTable with 11 column snippets, calc-map aggregation, keyboard cell-nav, and the `+ group` / `+ item` / `✕` row actions). **Regression harness**: `src/frontend/src/routes/dev/tree-table-demo/+page.svelte` (a static product-catalog fixture exercising the generic API, accessible at `/dev/tree-table-demo`). Columns may opt in to auto-collapse on narrow containers via `collapsible: true`; the threshold is configurable per-TreeTable through `collapseBreakpointPx` (default 900 px). The outer wrapper is horizontally scrollable, so content that exceeds the viewport stays reachable even when no columns collapse further. Per-row action buttons (the `rowActions` snippet) live in a dedicated trailing column by default; callers can pass `actionsPlacement="treeColumn"` to inline the actions inside the tree column instead — EstimationGrid uses this so its `+ group` / `+ item` / `✕` controls sit directly after the row title rather than off to the right past every value column. **A header label never paints outside its own column** (task-140): the header row (`data-testid="tt-header"`) is deliberately **normal-case** — `uppercase tracking-wide` cost ~20-25 % extra width for no legibility gain, which is what pushed labels out of their fixed tracks — and every header cell carries `min-w-0 overflow-hidden whitespace-normal break-words leading-tight`, with `items-end` on the row so a wrapped two-line label stays on the baseline of its single-line neighbours. Without that, a **single long word cannot wrap** and simply overflows its grid item, painting over the neighbouring header (DE "PESSIMISTISCH" needs ~108 px in a 6rem track's ~80 px content box). `overflow-hidden` is deliberately NOT applied to the data cells — they hold focusable `<input>`/`<select>` elements whose focus rings it would clip. `e2e/treetable-header-fit.test.ts` guards this by measuring `scrollWidth <= clientWidth` on every header cell across the PERT grid and both bucket-editor views, **in both locales** (the defect is translation-dependent, so a German-only check would let an English regression through); its English case runs under a dedicated `dev-estimator` user because the language preference is persisted per user and specs share one backend.

### Frontend — the one app header (`AppHeader`)

`src/frontend/src/lib/components/AppHeader.svelte` is the **single** top navigation, rendered by the root `+layout.svelte` on **every** route (task-141). Before it there were two divergent top bars — the root layout's inline header, hidden for `/sessions` via an `isSessionRoute` guard, and the session group's own chrome — so a user in a session room saw unfamiliar chrome with no recognisable way out. **Do not duplicate header markup into a route layout again**; add a destination to the component's `items` array instead. It renders the brand lockup (mark + wordmark, linking home), the horizontal menu, and `UserMenu`, above the brand gradient hairline; when `account` is `null` (the auth gate is showing the login dialog) only the lockup and hairline render.

The menu is a **flat row of `<a>`s inside a `<nav>`** — deliberately not a `<ul>`/`<li>` list, because `e2e/undo.test.ts` asserts a page-global `ul li` count of 0 and a nav list silently breaks it. A destination is active when the path equals its href **or starts with `href + '/'`**, so `/projects/{id}` keeps "Projects" marked and a room keeps "Sessions"; the active item gets `aria-current="page"` plus brand-green text and bottom border. `/estimations/**` sits under neither item and matches none — that is correct, not a gap. Each item's href comes from `resolve()` in the `items` array, which the `svelte/no-navigation-without-resolve` ESLint rule cannot follow, so the loop carries the same scoped `eslint-disable-next-line` the two computed-href call sites already use (`estimations/[id]/+page.svelte`, `VersionList.svelte`) — and the `<a href={item.href}` must stay on ONE line or the suppression lands on the wrong line. The per-page contextual back links (`project.pageBack`, `estimation.pageBack`, `compare.back`, `editor.back`, `session.summary.backToDraft`, `session.room.backToEstimation`) are unaffected: the menu is global navigation, they are local. `e2e/navigation.test.ts` pins the header on every route including a seeded session room, the active-item marking, and the way back out.

### Frontend — i18n (UI strings)

Frontend UI strings live in `svelte-i18n` JSON catalogs under `src/frontend/src/lib/i18n/` — **never** inline string literals in components (phase-16, task-124). `src/lib/i18n/index.ts` registers the `de` locale from `de.json`, calls `init({ fallbackLocale: 'de', initialLocale: 'de' })`, and exports `setUserLanguage(lang: SupportedLanguage)` (it drives the `locale` store off the domain enum's `code` — the same `SupportedLanguage` shared with the backend). Keys are dot-separated and component-scoped (`panel.parameters.title`, `history.conflict.body`, `editor.undoTooltip`). task-124 was a DE lift-and-shift (catalog holds the current verbatim text — mostly English today with German pockets — so there was no visible change). task-125 added `en.json` (mirrors `de.json` key-for-key), registered `'en'`, and a **language switcher** in `UserMenu.svelte` — a DE/EN `<select>` that `PUT`s `/api/auth/me/language` via `apiFetch` then `setUserLanguage(...)`, surfacing failures through a local `ErrorBanner` + `log.error`. Both providers populate `AuthAccount.language` from the backend: Entra via `fetchCurrentUserAccount`, and the **dev** provider's `loadAccount()` also fetches `GET /api/auth/me` for the `language` only (roles/displayName stay client-side per task-120), so a language switch **persists across a dev reload** too (task-127). Its e2e (`e2e/language.test.ts`) proves the reload-persistence under a dedicated `dev-estimator` user; `playwright.config.ts` pins `locale: 'de-DE'` so Accept-Language seeds fresh dev users German. Code↔enum mapping is `SupportedLanguage.values().find((v) => v.code === code)` (the domain `fromCode` helper is JVM-only, not `@JsExport`ed). The generic `treetable/TreeTable.svelte` and the `dev/tree-table-demo` fixture are intentionally left un-internationalised (generic / dev-only).

DEFAULT_LOCALE`, so the module never imports the i18n store and stays a leaf dependency; use `$locale` in markup, `get(locale)` in plain functions). **Never** call `.toFixed()`, `toLocale*()`, or hardcode a `de-DE` locale in a component — those were all migrated to the helper so English users see English grouping/date order. ### Logging

One logging approach per module — use it; do not invent a second mechanism.

- **Backend** (Quarkus): log via the static `io.quarkus.logging.Log` API (`Log.info/debug/warn/error`) — no per-class logger field. Levels are configured per profile in `application.properties`: app code (`io.github.theestimator`) at DEBUG in `%dev`/`%test`, INFO in `%prod`; the root level stays at the Quarkus default. The PROD profile emits structured JSON (`%prod.quarkus.log.console.json.enabled=true`, backed by the `quarkus-logging-json` dependency) for Kubernetes; the human-readable console stays the default in dev. `EstimationVersionService` is the reference site (INFO on create/submit/delete with the estimation id, DEBUG for finer detail, ERROR on failure paths). Every request carries a **correlation id** (task-026): `CorrelationIdFilter` (`io.github.theestimator.observability`, a JAX-RS request+response `@Provider`) reads the `X-Correlation-ID` header (or generates a UUID), puts it in the logging MDC under `correlationId` — so the JSON logs carry it per request — and echoes it back on the response header. Prometheus metrics are served at `/q/metrics` (Micrometer, `http_server_requests_*` timers) via `quarkus-micrometer-registry-prometheus`.
- **Domain** (Kotlin Multiplatform): use the `io.github.oshai:kotlin-logging` facade — `private val logger = KotlinLogging.logger {}` and the lambda form `logger.debug { "…" }` (allocation-free when the level is off). On the JVM target it delegates to slf4j (the backend supplies a provider via Quarkus' JBoss LogManager bridge; the domain's own JVM tests pull `slf4j-simple` as `runtimeOnly`); on the JS target it writes to the browser console, so the frontend sees domain logs in dev. Logging is observation only — never control flow; the business math stays the single source of truth.
- **Frontend** (SvelteKit): import `log` from `$lib/log.ts` (a configured `loglevel` instance — `debug` under `import.meta.env.DEV`, else `warn`). **Never write bare `console.*`.** The error-surfacing rule still holds: a `catch` must surface failure via `ErrorBanner` — `log.error(...)` is *in addition to*, not instead of, user-facing surfacing.

### Modular authentication and authorization

Auth is provider-modular. The active provider is picked by the backend property `app.auth.provider` and the matching frontend env var `VITE_AUTH_PROVIDER` — values `dev` | `entra` | `keycloak`. Backend SPI lives in `src/backend/implementation/src/main/kotlin/io/github/theestimator/auth/`: `AuthModule` (interface), `Role` (enum `VIEWER` / `ESTIMATOR` / `ADMIN`), `CurrentUser` (provider-agnostic principal), `CurrentUserProvider` (`@RequestScoped` bean populated by each concrete module via a filter or `SecurityIdentityAugmentor`), and `AuthConfig` (binds `app.auth.provider`). The `/api/auth/me` endpoint returns the current user. Frontend SPI lives in `src/frontend/src/lib/auth/`: `AuthProvider` interface (`init`/`login`/`logout`/`loadAccount`/`getAccount`/`getAuthorizationHeader`) and `getAuthProvider()` factory. Roles are **backend-authoritative** (task-120): the Entra provider's `loadAccount()` resolves the account — and its roles — from `GET /api/auth/me` (which derives roles from the access token), not from the id token, so Entra app roles only need to live on `estimation-api` and the UI can never disagree with backend enforcement; the shared `$lib/auth/currentUser.ts` maps the `CurrentUserDto` to `AuthAccount`. The dev provider's `loadAccount()` stays client-side (its hard-wired roles already match the backend dev augmentor). `getAccount()` returns the account already resolved by the awaited `loadAccount()` (the Entra provider caches it). The API wrapper `apiFetch` (`src/frontend/src/lib/api/fetch.ts`) consults `getAuthProvider().getAuthorizationHeader()` and attaches the result as the `Authorization` header on every `/api` call. Concrete providers land in task-006 (dev / hard-wired users — see `docs/auth-dev.md`), task-007 (Entra ID via MSAL + quarkus-oidc — see `docs/entra-setup.md`), and task-060 (Keycloak); resources, panels, and routes never touch provider specifics — they read `CurrentUserProvider` / `getAuthProvider()` only. `@RolesAllowed` is operational under both modules — the dev and Entra augmentors populate the `SecurityIdentity` with Quarkus role strings derived from `CurrentUserProvider` / OIDC claims respectively. The REST resources are **role-protected** (task-091): reads (GET) require `VIEWER`, writes (POST/PUT/DELETE) require `ESTIMATOR`, and `/api/admin/ping` requires `ADMIN`; an anonymous request → `401`, a wrong-role request → `403` (see `docs/authentication.md`). The dev module is **strict**: there is no default-user fallback, so a request without a valid `Authorization: Dev <subjectId>` header yields `401`. Its `Dev <subjectId>` header is **forgeable** (no token/signature), so it is fail-closed against production (task-092): `app.auth.provider` has no default value (a profile that omits it fails to start), and `AuthProviderGuard` (a `@Observes StartupEvent` bean) refuses to boot when the `dev` provider is active under a `NORMAL` launch. Tests authenticate via the `DevAdminAuth` JUnit5 extension (`src/backend/implementation/src/test/kotlin/io/github/theestimator/auth/DevAuthTestSupport.kt`).

**Just-in-time user provisioning**: the auth modules only populate an in-memory `CurrentUser`; a persisted `User` row is created on first sighting by `CurrentUserService.ensureUser(principal)` (keyed by the unique `entraSubjectId`). The reliable trigger is `UserProvisioningFilter` — a provider-agnostic `@Blocking` request filter (`auth/`) that provisions the current user on every authenticated **mutating** request (POST/PUT/PATCH/DELETE); `GET /api/auth/me` also provisions. This is what makes `User` FKs (audit, ownership, the undo log) resolvable. `ensureUser` takes the principal as a parameter (pure to test; no DB writes on the Vert.x event loop). Note the **dev** frontend builds its account client-side and does **not** call `/api/auth/me`, so for dev the filter — not `/me` — is what provisions users. The **Entra** frontend, however, now calls `GET /api/auth/me` on load (task-120, to read backend-authoritative roles), and `/me` provisions too — so under Entra either path provisions the user.

**Per-user language preference** (phase-16, task-123): the `users.language char(2) NOT NULL DEFAULT 'de'` column (`V12`) persists each user's UI language. `SupportedLanguage` (`io.github.theestimator.i18n`, a `@JsExport` enum `DE`/`EN` with an ISO `code`, shared with the frontend via the `typescriptDist`) is the one canonical name both sides use; the top-level `fromCode(code)` bridges wire/DB codes to it. `ensureUser(principal, requestedLanguage? = null)` **seeds** the language on first sighting only — from the request's `Accept-Language` (`en` → `EN`, otherwise `DE`), applied by both the mutating-request `UserProvisioningFilter` and `GET /api/auth/me` — and never overwrites an existing user's stored choice. `CurrentUserService.updateLanguage(principal, language)` persists an explicit choice (the PUT endpoint above). Language lives on the `User` row, never on the token-derived `CurrentUser` principal.

## REST API surface

Every JSON endpoint documents its **request and response** schemas plus real status codes (401/403/404/409/204) in the generated OpenAPI document (task-094). Authorization failures carry a structured JSON body `{ "message": …, "status": … }` via `ForbiddenExceptionMapper` (403) / `UnauthorizedExceptionMapper` (401) in `rest/error/AuthorizationExceptionMappers.kt` (task-093) — user `ExceptionMapper`s that override Quarkus' built-in defaults for `io.quarkus.security.{Forbidden,Unauthorized}Exception`, logging the denial (WARN/INFO) with the request path. The JAX-RS methods keep their `jakarta.ws.rs.core.Response` return type; response bodies are declared with MicroProfile OpenAPI annotations (`@APIResponse` + `@Content`/`@Schema`, `@Tag`, `@Operation`). SmallRye writes the document to `src/backend/implementation/target/openapi/openapi.json` during augmentation (`quarkus.smallrye-openapi.store-schema-directory`), and **the Gradle build carries it into the frontend** (task-114): `:backend:implementation` snapshots it to `build/openapi/` and publishes it through the consumable `openapiSchema` configuration; `:frontend` resolves it via `backendOpenapi`, and `syncBackendOpenapi` refreshes the committed `src/frontend/src/lib/api/openapi.json` before `genApi` regenerates `schema.d.ts`. So `./gradlew build` keeps both files current — **commit them with the change that caused them**; no manual `cp`/`npm run gen:api` step. Two traps the wiring works around, do not undo them: the document is written as a SIDE EFFECT of augmentation into a path no Quarkus task declares as an output, so `quarkusAppPartsBuild` gets an explicit `outputs.file(...)` or a cached/up-to-date augmentation silently leaves it missing; and BOTH the prod augmentation (`%prod` → OIDC, emits `securitySchemes`) and the `@QuarkusTest` augmentation (`%test` → dev auth, does not) write that same path, so `test` is ordered `mustRunAfter` the snapshot to pin the **prod** contract — the one that describes the deployed API. The document is also pinned to be **environment-independent** (task-135): `quarkus.smallrye-openapi.security-scheme=oidc` + `quarkus.smallrye-openapi.oidc-open-id-connect-url=https://login.microsoftonline.com/common/v2.0/.well-known/openid-configuration` in `application.properties`. Without them Quarkus derives the documented `openIdConnectUrl` from the OIDC config resolved at augmentation (`%prod.quarkus.oidc.auth-server-url`, which interpolates `${ENTRA_TENANT_ID}`), so the committed schema — and therefore the drift gate — depended on whether the building shell had that variable set, and a real tenant UUID was committed as build output. **Both** properties are required: the URL alone is only a fallback that auto-detection overrides whenever the live OIDC config resolves; `security-scheme=oidc` selects the explicit path so the pin wins. This is documentation-only and does NOT change runtime OIDC. The drift gate `:frontend:verifyOpenApiSchemaCommitted` (`git diff --exit-code --stat HEAD`, so `git add`-ing a stale schema cannot satisfy it) is **opt-in**: it joins `check` only when `CI` is set or `-PopenApiGate` is passed. That is deliberate — wiring it in unconditionally would fail every local build that touches a REST DTO until the regenerated files were committed, while the task workflow requires a green build *before* the commit. (Frontend component code still consumes the hand-written `$lib/api/types.ts`; migrating it onto the generated `schema.d.ts` is a separate follow-up.)

`GET /api/estimations/{id}` returns `EstimationDetailDto` which carries `method: EstimationMethod` and `methodDescription: String` — the description is a human-readable English string sourced from `EstimationMethodModule.description` (task-119), rendered verbatim in the frontend method-detail popover.

Base path `/api/`. Key endpoints under `EstimationVersionResource`:

- `GET  /api/estimations/{eid}/versions` — list (draft first, then submitted)
- `POST /api/estimations/{eid}/versions` — create draft (clones from latest submitted if any)
- `GET  /api/estimations/{eid}/versions/draft` — returns the draft with **on-the-fly calculated** values
- `PUT  /api/estimations/{eid}/versions/draft` — body is `DraftUpdateDto`; replaces collections wholesale
- `POST /api/estimations/{eid}/versions/draft/submit` — snapshot draft → SubmittedEstimationVersion
- `POST /api/estimations/{eid}/versions/draft/undo` — undo this user's last mutation → recalculated draft; `409` (`ConflictDetailsDto`) if a newer change blocks it (task-075)
- `POST /api/estimations/{eid}/versions/draft/redo` — redo the last undone mutation → recalculated draft; `409` on conflict
- `GET  /api/estimations/{eid}/versions/draft/history` — the draft's mutation log (`List<MutationLogEntryDto>`, ACTIVE + UNDONE, ordered by sequence)
- `GET  /api/estimations/{eid}/versions/{n}` — read a submitted version (stored calc values)
- `GET  /api/estimations/{eid}/versions/{a}/compare/{b}` — diff (use `draft` for the live draft)
- `GET  /api/estimations/{eid}/versions/{n}/export?format=xlsx|csv` — exports
- `POST /api/estimations/{eid}/versions/import/merlin` — import a Merlin project WBS as a new draft version (multipart `file`; `409` if a draft already exists, `400` if the upload is unreadable). See "Merlin WBS import" below.
- `POST /api/estimations/{eid}/versions/{n}/export/merlin?overwriteStructure=` — write this version's calculated effort back into an uploaded Merlin document and return the modified **copy** (multipart `file`; `409` + `MerlinStructureDiffDto` when the structure drifted, `400` if the upload is unreadable). See "Merlin effort export" below.

**Merlin WBS import** (task-131): `MerlinImporter` (`io.github.theestimator.service`, alongside `ExcelImporter`) turns a **Merlin Project** document's Work Breakdown Structure into a new draft version. A `.mproject` is a macOS bundle whose `state.sql` is a **SQLite 3 database** (an Apple Core Data store, `Z`-prefixed tables); activities live in `ZSCHEDULEITEM` (`ZTITLE`, `ZPARENTACTIVITY_` for hierarchy, `ZORDERINPARENTACTIVITY`, `ZISMILESTONE`, `ZGIVENWORK_` = a short string like `"1d"`). Activities are filtered by `ZTITLE IS NOT NULL` (resource-assignment rows have no title; **do not** gate on the version-specific `Z_ENT`). The upload is accepted either as a **zipped** `.mproject` (the importer finds the `state.sql` entry) or the raw `state.sql`; it is read via a plain `org.xerial:sqlite-jdbc` `DriverManager` connection on a temp file — **not** a Quarkus datasource (the app DB stays PostgreSQL). Work maps to person-days (d×1, w×5, h×0.125) and a single value seeds optimistic=likely=pessimistic (task's "single work → triple"). Output **preserves the WBS tree (groups + nesting) for both methods**; only the leaf type is method-specific (off `estimation.method`): `THREE_POINT_PERT` → `DraftFixedItemNode`, `BUCKET_SAMPLED_PERT` → `DraftBucketedItemNode` assigned to a single "Imported" bucket (`isSample` = has work). Buckets classify items; they do NOT replace the tree grouping. `EstimationVersionService.importMerlinDraft` guards "one draft at a time" (`409`) and does the version-numbering/persistence like `createDraft`; the frontend control is on the estimation detail page.

**Upload size is a GATEWAY concern, and it is cluster-only.** Both Merlin endpoints POST a whole `.mproject` as multipart — real documents are several MB (even the committed `planning/inputdata/MerlinDemoProject.mproject/state.sql` is 1.5 MB). nginx' default `client_max_body_size` is **1m**, so in the cluster a normal-sized Merlin file was rejected with a bare `413` *before* being proxied: nothing reached the backend, nothing appeared in the backend log, and only `kubectl logs deploy/frontend` showed `client intended to send too large body`. Local dev never reproduces it — the Vite dev proxy imposes no limit — and neither does the Playwright suite, which also goes through Vite; **no test covers the gateway config**. `src/frontend/nginx.conf` therefore sets `client_max_body_size 32m` on `location /api/`, matched by `quarkus.http.limits.max-body-size=32M` (Quarkus' own default is 10M). Keep the two numbers in sync: the smaller one is the effective limit, and raising only one just moves the rejection one hop. A change here lives in the frontend IMAGE, so it needs a rebuild + redeploy, not a `kubectl apply`.

**Merlin effort export** (task-133): `MerlinExporter` (same package) is the mirror of the importer — it writes the estimation's results back into a Merlin document. It **only ever edits a COPY**: the uploaded bytes go to a temp file, are modified there, and are streamed back as an attachment download; the user's own `.mproject` is never touched (a zipped upload is repacked with only its `state.sql` entry swapped). The value written is the calculated **`offerPT`** (mean + risk surcharge) of each **LEAF** — Merlin derives a parent's work from its children, so group activities are left alone — encoded into `ZGIVENWORK_` exactly as Merlin writes it: ASCII `"<days>d"` plus a trailing `0x3F` marker byte (`X'31643F'` is `"1d?"`), with `Z_OPT` bumped on every changed row and `NULL` written for a leaf with no effort. The version is resolved by the resource's existing `resolveVersion(...)` helper, so `draft` and a submitted number both work and `MerlinExporter` consumes the same `SubmittedEstimationVersion` the xlsx/csv exporters take. The frontend picks that ref itself (`exportVersionRef`): the draft while one exists, otherwise the **highest submitted version** — submitting CONSUMES the draft, so hardcoding `draft` would 404 exactly when the estimate is finished and you want it back in Merlin (the button is disabled when the offer has no version at all). **Correlation is by WBS path** (titles joined with `" / "`), the only key the import leaves behind — so before writing anything the exporter compares the ordered path lists of both sides and, on drift, throws `MerlinStructureChangedException` → `409` `MerlinStructureDiffDto` (`missingInMerlin` / `missingInEstimation` / `reordered`). The protocol is **stateless**: the frontend re-POSTs the same file with `?overwriteStructure=true` once the user confirms in `MerlinStructureDialog.svelte`. That overwrite **reconciles by path** rather than wiping and rebuilding — activities that still exist keep their row (and their dates, dependencies and assignments), missing ones are INSERTed, and obsolete ones are DELETEd together with the assignment rows referencing them via `ZACTIVITY_`. New rows take their `Z_PK` from the Core Data `Z_PRIMARYKEY` table using the row for **`Z_ENT = 48`** (`ScheduleItem`, the ROOT of the hierarchy `Activity`=49 and `Assignment`=51 inherit from — the subclass rows carry `Z_MAX = 0` and must not be used) and get a fresh 22-char URL-safe base64 `ZUNIQUEID`. **A Merlin title may itself contain the `" / "` separator** (the sample has `"… Layer-2 / Layer-3"`), so a node's parent and title are captured during the tree walk and never recovered by splitting the path string — doing that reparents such activities to the root.

Auth endpoints (provider-agnostic, populated by whichever concrete module is active):

- `GET  /api/auth/me` — current user as `CurrentUserDto` (subjectId, email, displayName, roles, providerName, **`language`**) or `401` when no user is populated for the request. `language` is the persisted `users.language` code (`de`/`en`), read off the provisioned `User` row (not the token principal).
- `PUT  /api/auth/me/language` — body `{ "language": "de" | "en" }`; persists the current user's language preference and returns `204`. An unsupported code → `400`. The code is validated against the shared `SupportedLanguage` enum (`fromCode`); persistence goes through `CurrentUserService.updateLanguage` (logs INFO with the user id + new language).
- `GET  /api/admin/ping` — `@RolesAllowed("ADMIN")` canary that returns `{message: "pong", user: <subjectId>}`. Used by `e2e/auth.test.ts` to prove role enforcement under the dev module; survives feature churn.

`DraftUpdateDto.roots: List<EstimationNodeUpdateDto>` carries the editable tree (recursive children, `type` discriminator). Responses use `EstimationNodeDto` with calculated fields populated at every level (groups carry accumulated values). Both leaf DTOs are **flat data classes** with a `type: String` discriminator (`@Schema(enumeration = ["GROUP","FIXED","TIME_RELATIVE","BUCKETED"])`) — no Jackson polymorphism. `BUCKETED` is **reserved** (task-100) for the bucket+sampled method, with `bucketId` / `isSample` fields on the flat DTO; `DraftUpdateApplier` currently rejects any `type: "BUCKETED"` node with `400` (a WARN is logged) pending task-103's persistence path.

`POST /api/projects/{id}/estimations` (`ProjectResource.createEstimation`) accepts an `EstimationCreateDto` whose `method: EstimationMethod` selects the estimation method (defaults to `THREE_POINT_PERT` when omitted); the estimation read DTOs (`EstimationSummaryDto`, `EstimationDetailDto`) return it. The method is immutable — there is no estimation-update endpoint, so it cannot change after creation.

**Collaborative estimation sessions** (`SessionResource`, phase-11 task-064) under base path `/api/sessions`, all `@RolesAllowed("ESTIMATOR")`; moderator-only actions additionally check the caller's subjectId equals the session's `moderator_subject_id` (→ `403`), and vote/phase state guards return `409`. Every mutation returns the full `SessionDto` and fires `SessionEventPublisher` (a CDI `Event<SessionChangedEvent>` that the task-065 WebSocket layer will observe). `POST /api/sessions` (moderator = caller; body `{estimationId, title, itemLogicalIds, moderatorEstimates?}` — `moderatorEstimates` defaults true (task-129); when false the moderator only moderates and a vote from them is `409`; also exposed on `SessionDto.moderatorEstimates`; `400` if a logicalId is not a draft leaf), `GET /api/sessions/{id}`, `GET /api/sessions?estimationId=…` (the `estimationId` query param is **optional** — task-128; omit it to list all joinable CREATED/RUNNING sessions across every estimation, via `EstimationSessionService.listJoinableSessions()` / `EstimationSessionRepository.findJoinable()`, which powers the frontend's open-sessions join list), `POST …/{id}/join` (idempotent ESTIMATOR participant), `POST …/{id}/start` (CREATED→RUNNING), `PUT …/{id}/items/current/notes`, `POST …/{id}/items/current/phase2` (reveal), `POST …/{id}/items/current/finalize` (writes the aggregate mean triple back onto the draft leaf **through the draft-update path** so the change is undoable, and appends the item's discussion notes — prefixed with the session name — to that leaf's `assumptions` in the same write (task-129), then advances), `POST …/{id}/votes` (upsert the current-item current-phase vote), `POST …/{id}/agree`, `POST …/{id}/cancel`. During a blind PHASE1 an item exposes only `submittedVoteCount`; votes + the aggregate appear once the item is PHASE2/FINALIZED. Mean/spread/divergence is **never computed in the service** — since task-105 both reduction call sites (`finalizeCurrent` and the `itemDto` builder) dispatch through `EstimationMethodRegistry.requireSession(session.estimation.method).reduce(...)`, which for PERT delegates to the domain `VoteAggregation.aggregate(...)` (task-062). `itemDto` has no access to the estimation, so `buildDto` resolves the support **once per DTO build** and passes it down as a parameter. Since task-142 the SPI speaks `SessionVoteInput`/`SessionReduction`, so a single private `reducePert(support, votes)` helper does the `PertVoteInput` wrap and the `PertReduction` unwrap for both call sites — that helper is deliberately the **only** place in the service that assumes votes are a three-point triple, because `session_votes` has no bucket column until task-106 extends it, and it is where the second branch will grow. The frontend still calls the `aggregateVotes` bridge directly — the SPI and registry are domain-internal, so a JS-side dispatch would need a new `@JsExport` bridge, deferred to task-106 where a second method actually diverges.

**Realtime session channel** (`SessionSocket`, phase-11 task-065): a **push-only** WebSocket at `/ws/sessions/{sessionId}` (`quarkus-websockets-next`) broadcasts the fresh `SessionDto` to every joined connection whenever state changes — mutations still go **only** through the REST control plane. `SessionBroadcaster` observes task-064's `SessionChangedEvent` (`@Observes(during = AFTER_SUCCESS)`, so it pushes committed state without socket I/O inside the transaction) and sends the **same** payload to all connections (PHASE1 hiding is already uniform, so no per-recipient scoping). Server→client messages: `{type:"session", session: SessionDto}` on every change (and on connect), `{type:"error", message}` on a handshake problem. **Browser auth:** browsers can't set an `Authorization` header on a WS handshake and auth is provider-specific, so a joined participant first `POST`s `/api/sessions/{id}/ws-ticket` (ESTIMATOR + participant → `403`/`404` otherwise) to mint a short-lived, single-use opaque ticket (`SessionTicketStore`, ~30s TTL), then opens `ws://…/ws/sessions/{id}?ticket=…`; `@OnOpen` consumes the ticket (matching sessionId), re-confirms participation, and otherwise closes with a policy-violation (1008).

**Frontend session UI** (phase-11 task-066): a route group under `src/frontend/src/routes/sessions/`. It used to be a **separated** group with its own room chrome (a mark + "The Estimator · Session" label + a small "Verlassen" link) while the root header was hidden for `/sessions` — that made the room look unlike the rest of the app and left no recognisable way back, so task-141 deleted it: `sessions/+layout.svelte` is now **only** the room background wrapper (`bg-gray-50`, deliberately WITHOUT `min-h-screen` — that was right while this layout WAS the whole screen, but stacked under the global header it pushes every session page past the fold and leaves a permanent scrollbar over dead space; the grey therefore ends with the content), and the shared `AppHeader` navigates here like everywhere else. **Two-phase session flow** (phase-11 task-067): the room page picks a panel from `store.session.status`/`currentPhase` and mounts one of three components under `$lib/session/`. On mount an estimator auto-joins (idempotent) and, once CREATED, the moderator starts the session. `PhaseOnePanel.svelte` — every participant (the moderator estimates too) submits a **blind** PERT triple (only the submitted/total count is ever shown, never others' numbers); the moderator additionally edits the shared discussion notes (debounced PUT) and reveals PHASE2. `PhaseTwoPanel.svelte` — reveals the votes table + the aggregate (mean triple, PERT mean, and the spread: range / std-dev / coefficient of variation), with an amber highlight when `diverged`; estimators may submit a revised triple + toggle "I agree"; the moderator finalizes. The mean/spread is **never** hand-rolled in the component — it is computed by the domain `VoteAggregation` (task-062) reached through the JS-friendly `aggregateVotes(Array<EstimatorVote>)` factory in `DomainFactory.kt` (the same Kotlin/JS-bundle pattern `adapter.ts` uses), so it is the single source of truth and matches the backend `AggregateDto` byte-for-byte (asserted in `e2e/session.test.ts`). `SessionSummary.svelte` renders the FINALIZED per-item final triples + a link back to the estimation (finalize wrote those values onto the draft leaves through the draft-update path, so they are undoable). All numeric display goes through `$lib/format.ts`; all strings through the `session.*` i18n keys; every error path both `log.error`s and surfaces via `ErrorBanner`. See `docs/estimation-sessions.md`.
