# REST resources

Loads when working under `src/backend/implementation/src/main/kotlin/io/pythia/rest/`. The backend-wide rules are in `src/backend/CLAUDE.md`.

### Endpoint notes that the OpenAPI document does not carry

`EstimationVersionResource` (base `/api/estimations/{eid}/versions`): list, create draft (clones from latest submitted if any), `GET …/draft` returns the draft with **on-the-fly calculated** values, `PUT …/draft` takes a `DraftUpdateDto` and replaces collections wholesale, `…/draft/submit` snapshots draft → `SubmittedEstimationVersion`, `…/draft/undo` and `…/draft/redo` return a recalculated draft or `409` (`ConflictDetailsDto`) when a newer change blocks it (task-075), `…/draft/history` returns the mutation log (ACTIVE + UNDONE, ordered by sequence), `GET …/{n}` reads a submitted version (stored calc values), `…/{a}/compare/{b}` diffs (use `draft` for the live draft), and `…/{n}/export?format=xlsx|csv` exports. The two Merlin endpoints are covered by the `merlin-integration` skill.

`GET /api/estimations/{id}` returns `EstimationDetailDto` which carries `method: EstimationMethod` and `methodDescription: String` — the description is a human-readable English string sourced from `EstimationMethodModule.description` (task-119), rendered verbatim in the frontend method-detail popover.

`DraftUpdateDto.roots: List<EstimationNodeUpdateDto>` carries the editable tree (recursive children, `type` discriminator). Responses use `EstimationNodeDto` with calculated fields populated at every level (groups carry accumulated values). Both leaf DTOs are **flat data classes** with a `type: String` discriminator (`@Schema(enumeration = ["GROUP","FIXED","TIME_RELATIVE","BUCKETED"])`) — no Jackson polymorphism.

`POST /api/projects/{id}/estimations` (`ProjectResource.createEstimation`) accepts an `EstimationCreateDto` whose `method: EstimationMethod` selects the estimation method (defaults to `THREE_POINT_PERT` when omitted); the estimation read DTOs (`EstimationSummaryDto`, `EstimationDetailDto`) return it. The method is immutable — there is no estimation-update endpoint, so it cannot change after creation.

**Project ownership (task-200).** `projects.owner_id` existed since V1 but was never written; now the creator becomes the owner (`createProject` provisions the caller via `ensureUser`). `GET /api/projects?owner=me` lists only the caller's projects; any other `owner` value is `400`. Reads resolve the caller **read-only** (`CurrentUserService.findUser`, not `ensureUser`): GETs never provision (see JIT provisioning in `auth/CLAUDE.md`), so a caller without a `User` row gets an empty list and `canChangeOwner: false` unless an admin. `ProjectSummaryDto`/`ProjectDetailDto` carry `owner` (`UserRefDto`, `null` for a legacy project, which only an admin can assign) and `canChangeOwner`, both computed by `ProjectService.mayChangeOwner` — the single place the rule lives. `PUT /api/projects/{id}/owner` (`{ownerId}`) transfers ownership: `@RolesAllowed("ESTIMATOR","ADMIN")`, then owner-or-ADMIN (`403` otherwise), `400` for an unknown user, `404` for an unknown project. Ownership is transferred, never removed. The resource method is itself `@Transactional` because the detail mapper reads the lazy `estimations` after the service returns; without it the response is a `LazyInitializationException` `500`. `GET /api/users` (`UserResource`, VIEWER) lists only **provisioned** users, sorted by display name — someone who has never used Pythia cannot be picked. The dev seeder adds three colleagues (`testdata/SeededUsers.kt`, `providerName "seed"`) and an archived, unowned "Intranet-Relaunch 2024", so the demo data shows every owner case.

Auth endpoints (provider-agnostic, populated by whichever concrete module is active):

- `GET  /api/auth/me` — current user as `CurrentUserDto` (subjectId, email, displayName, roles, providerName, **`language`**) or `401` for an anonymous request — since task-202 that 401 comes from the class-level `@Authenticated` (any authenticated principal, no role required) with the structured `{message, status}` body; the method's own null check stays as defence in depth. `language` is the persisted `users.language` code (`de`/`en`), read off the provisioned `User` row (not the token principal).
- `PUT  /api/auth/me/language` — body `{ "language": "de" | "en" }`; persists the current user's language preference and returns `204`. An unsupported code → `400`. The code is validated against the shared `SupportedLanguage` enum (`fromCode`); persistence goes through `CurrentUserService.updateLanguage` (logs INFO with the user id + new language).
- `GET  /api/admin/ping` — `@RolesAllowed("ADMIN")` canary that returns `{message: "pong", user: <subjectId>}`. Used by `e2e/auth.test.ts` to prove role enforcement under the dev module; survives feature churn.

### The dev-only test-data endpoint (task-176)

`DELETE /api/dev/test-data` (`rest/TestDataResource.kt`, task-176) is the one endpoint deliberately **outside** that contract: it is annotated `@IfBuildProfile("dev")`, so the class is not registered in a prod build and the path cannot exist in a deployed image — which is why the e2e cleanup got a dev-only endpoint rather than a `DELETE /api/projects/{id}` on the production surface. It is `@RolesAllowed("ADMIN")` on top of that, and returns `{deletedProjects, deletedSessions, remainingProjects}`. It deletes everything except the `SeededProjects.ALL` names, and **the deletion order is load-bearing**: session votes first, then the sessions (whose `cascade = ALL` takes items and participants with them), then the projects. Two ways to get it wrong, both of which produce an FK violation rather than a silent miss: a bulk JPQL `delete from EstimationSession` runs no JPA cascade at all, because bulk operations bypass the persistence context; and removing the session entities without clearing votes first deletes `session_items` out from under the `session_votes` FK, since votes are queried rather than mapped as a cascading collection.
