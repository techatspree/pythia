# Persistence (JPA entities)

Loads when working under `src/backend/implementation/src/main/kotlin/io/pythia/domain/`. The backend-wide rules are in `src/backend/CLAUDE.md`.

## Persistence shape

The `estimations` table carries a method column (`method`, `VARCHAR(255)`, V9 migration; JPA `@Enumerated(STRING) var method: EstimationMethod`) — the estimation's `EstimationMethod`, chosen at creation and **immutable** (there is no estimation-update endpoint, so nothing mutates it after create). Every version of one estimation shares its method.

Single self-referential table per side, JPA `SINGLE_TABLE` inheritance with a `node_type` discriminator (`GROUP` | `FIXED` | `TIME_RELATIVE` | `BUCKETED`). Children ordered by an integer `position` column (`@OrderColumn`). The version's `roots` use `@SQLRestriction("parent_id IS NULL")` to pick out the top-level rows.

- **Draft** side: `draft_estimation_nodes` (V6 migration); JPA entity `DraftEstimationNode` with three `@DiscriminatorValue` subclasses (`DraftGroupNode`, `DraftFixedItemNode`, `DraftTimeRelativeItemNode`). Mutable, edited via the REST PUT endpoint.
- **Submitted** side: `submitted_estimation_nodes` (V7 migration); mirrors the draft shape with `SubmittedEstimationNode` + `SubmittedGroupNode`/`SubmittedFixedItemNode`/`SubmittedTimeRelativeItemNode`/`SubmittedBucketedItemNode`. **Submitted entities are immutable snapshots** that store the calculated values directly on every row (mean, offerPT, cost, …); group rows store accumulated values for their subtree. `BUCKETED` rows additionally persist the raw method-specific input (`bucket_id`, `is_sample`, and the sample triple in `min/expected/max`) so a detail view or export can reproduce the input. The backend never recomputes on read.

### Buckets — and the migration/entity parity lesson

**Buckets** (bucket + sampled method, V10 migration): the `estimation_buckets` table (`id`, `estimation_id` FK `ON DELETE CASCADE`, `position`, `label`, `UNIQUE(estimation_id, position)`) is owned by the `Estimation` (`Estimation.buckets`, ordered by `position`) and shared across its draft + submitted versions. The bucket `id` is **client-assigned** (like a node's `logicalId`, not `@GeneratedValue`) so a single draft PUT can send new buckets together with the leaves that reference them. Both node tables gain a nullable `bucket_id` (FK `ON DELETE RESTRICT`) and `is_sample` column; the `BUCKETED` `@DiscriminatorValue` subclasses (`DraftBucketedItemNode` / `SubmittedBucketedItemNode`) carry the `@ManyToOne bucket` + `isSample` and **reuse the existing `min_effort`/`expected_effort`/`max_effort` columns** for a sample's optimistic/likely/pessimistic triple (non-samples leave them NULL and inherit the bucket average via `calculate()`). `DraftUpdateApplier.applyBuckets` upserts `estimation.buckets` by id (not clear-and-rebuild, since nodes FK-reference them) and runs before `applyRoots`; a `BUCKETED` leaf is accepted only when `estimation.method == BUCKET_SAMPLED_PERT` (else `400` + `Log.warn`) and its `bucketId` must resolve to an existing bucket. `DraftSnapshotMapper` captures the buckets so undo/redo round-trips them; `EstimationDetailDto.buckets` exposes them on the wire.

**Reordering buckets swaps `position` values**, which `applyBuckets` writes as row-by-row UPDATEs — and `UNIQUE(estimation_id, position)` is evaluated by PostgreSQL after EVERY statement, so the transient mid-swap duplicate aborted the transaction ("could not be saved", reorder lost). Two things keep that correct and must not be undone: `applyBuckets` first parks every existing bucket on a temporary NEGATIVE position and flushes, so no final position can collide with a stale one; and `V15` makes the constraint `DEFERRABLE INITIALLY DEFERRED` in the Flyway-managed schemas.

The constraint is ALSO declared on the `EstimationBucket` entity — deliberately, for **dev/prod schema parity**: `%test`/`%dev` build the schema from Hibernate (`drop-and-create`, Flyway off) while prod/dev-minikube use Flyway, so without the entity-level declaration the local schema had no such constraint at all and this bug was literally unreproducible outside the cluster. **When adding a constraint in a migration, add it to the entity too, or it will not exist where you test.**

### Schedule inputs (task-156)

The two inputs `EstimationVersion.schedule(dependencies, teamFte)` takes (task-155) are persisted on **both** sides, because a submitted snapshot that lost them would render a different Gantt than the draft it came from: a `team_fte DOUBLE PRECISION NOT NULL DEFAULT 1` column on `draft_estimation_versions` / `submitted_estimation_versions`, plus `draft_schedule_dependencies` / `submitted_schedule_dependencies` (`id`, `version_id` FK `ON DELETE CASCADE`, `from_logical_id`, `to_logical_id`) — `V19`. The default of 1 matters: `0` is the one team size task-155 rejects, so every pre-existing row stays schedulable. They ride the existing version payload (`EstimationVersionDto.teamFte`/`.dependencies`, optional on `DraftUpdateDto`); there is no separate resource. They are deliberately NOT fields on the KMP `EstimationVersion` — the domain takes them as parameters, so `DraftVersionMapper` is untouched.

`UNIQUE (version_id, from_logical_id, to_logical_id)` is declared on the **entities** as well as in the migration, per the V15 parity rule above — `%test` builds the schema from Hibernate, so a migration-only constraint would be absent exactly where `ProjectScheduleInputsIT` exercises it.

**That constraint plus clear-and-rebuild is the trap.** `DraftUpdateApplier.applyScheduleDependencies` clears the collection and re-adds, and Hibernate orders INSERTs ahead of orphan-removal DELETEs while PostgreSQL evaluates the constraint after every statement — so re-saving an **unchanged** edge list (the common case) transiently held two copies of the same edge and aborted the transaction. It therefore flushes after the clear. Same family as the bucket-reorder bug; here a plain flush suffices because this is a pure rebuild rather than an in-place swap.

**Three paths copy the schedule, and they are different files** — missing any one loses it in a different way: `EstimationVersionService.snapshotDraft` (draft → submitted, or a submitted version has no schedule), `EstimationVersionService.cloneFromSubmitted` (submitted → new draft, or continuing an estimate silently starts over), and `DraftSnapshotMapper.toUpdateDto()` (the undo capture — omit it and `apply(draft, draft.toUpdateDto())` stops being an identity, so an undo wipes the schedule). Each has a test.

An edge naming a `logicalId` that is not a current root is **accepted** on write: task-155 ignores unknown ids when it computes, so rejecting them here would make a root deletion fail a later save.

### Undo log

**Undo log** (V8 migration): `draft_estimation_versions` gains a `revision` counter plus `last_modified_by` / `last_modified_at` audit columns, and a new append-only `draft_mutation_log` table records one row per applied `DraftMutation` (`DraftMutationLogEntry`): monotonic `sequence_number` per draft, `revision_before`/`revision_after`, `kind` discriminator, `payload` + `inverse_payload` (`jsonb`, mapped `String` via `@JdbcTypeCode(SqlTypes.JSON)`), and an `ACTIVE`/`UNDONE` status. Finders live on `DraftMutationLogRepository`. `UndoService` records one entry per draft-changing `updateDraft` (skipping no-op PUTs via `EstimationVersion.diff`), and provides per-user `undoLastForUser` / `redoLastForUser` (restoring the stored `DraftUpdateDto` snapshot via `DraftUpdateApplier`) plus `historyFor`; a cross-user change on top of the target raises `UndoConflictException`. Snapshots are stored as `StoredMutation(kind, before, after)` DTO JSON (`DraftMutationJackson`), not raw domain types. Submitting a draft cascade-deletes its log.
