# Authentication and authorization

Loads when working under `src/backend/implementation/src/main/kotlin/io/pythia/auth/`. The backend-wide rules are in `src/backend/CLAUDE.md`.

## Modular authentication and authorization

Auth is provider-modular. The active provider is picked by the backend property `app.auth.provider` and the matching frontend env var `VITE_AUTH_PROVIDER` — values `dev` | `entra` | `keycloak`. Backend SPI lives in `src/backend/implementation/src/main/kotlin/io/pythia/auth/`: `AuthModule` (interface), `Role` (enum `VIEWER` / `ESTIMATOR` / `ADMIN`), `CurrentUser` (provider-agnostic principal), `CurrentUserProvider` (`@RequestScoped` bean populated by each concrete module via a filter or `SecurityIdentityAugmentor`), and `AuthConfig` (binds `app.auth.provider`). The `/api/auth/me` endpoint returns the current user. Frontend SPI lives in `src/frontend/src/lib/auth/`: `AuthProvider` interface (`init`/`login`/`logout`/`loadAccount`/`getAccount`/`getAuthorizationHeader`) and `getAuthProvider()` factory.

Roles are **backend-authoritative** (task-120): the Entra provider's `loadAccount()` resolves the account — and its roles — from `GET /api/auth/me` (which derives roles from the access token), not from the id token, so Entra app roles only need to live on `estimation-api` and the UI can never disagree with backend enforcement; the shared `$lib/auth/currentUser.ts` maps the `CurrentUserDto` to `AuthAccount`. The dev provider's `loadAccount()` stays client-side (its hard-wired roles already match the backend dev augmentor). `getAccount()` returns the account already resolved by the awaited `loadAccount()` (the Entra provider caches it). The API wrapper `apiFetch` consults `getAuthProvider().getAuthorizationHeader()` and attaches the result as the `Authorization` header on every `/api` call.

Concrete providers land in task-006 (dev / hard-wired users — see `docs/auth-dev.md`), task-007 (Entra ID via MSAL + quarkus-oidc — see `docs/entra-setup.md`), and task-060 (Keycloak); resources, panels, and routes never touch provider specifics — they read `CurrentUserProvider` / `getAuthProvider()` only. `@RolesAllowed` is operational under both modules — the dev and Entra augmentors populate the `SecurityIdentity` with Quarkus role strings derived from `CurrentUserProvider` / OIDC claims respectively. The REST resources are **role-protected** (task-091): reads (GET) require `VIEWER`, writes (POST/PUT/DELETE) require `ESTIMATOR`, and `/api/admin/ping` requires `ADMIN`; an anonymous request → `401`, a wrong-role request → `403` (see `docs/authentication.md`).

The dev module is **strict**: there is no default-user fallback, so a request without a valid `Authorization: Dev <subjectId>` header yields `401`. Its `Dev <subjectId>` header is **forgeable** (no token/signature), so it is fail-closed against production (task-092): `app.auth.provider` has no default value (a profile that omits it fails to start), and `AuthProviderGuard` (a `@Observes StartupEvent` bean) refuses to boot when the `dev` provider is active under a `NORMAL` launch. Module beans are gated at BUILD time (task-194): the dev beans need the explicit build value `dev` (`@IfBuildProperty`), while the Entra beans are `@UnlessBuildProperty(... "dev", enableIfMissing = true)` and so are in every non-dev build, including `%prod`, where the provider is missing at augmentation. Because the provider itself arrives at RUNTIME from the ConfigMap, the guard's second condition refuses to boot when it names no `AuthModule` in the build (logging the modules that are), instead of starting a backend that authenticates nobody. Changing `APP_AUTH_PROVIDER` between local builds needs `quarkusAppPartsBuild --rerun` (where augmentation runs; `quarkusBuild --rerun` only re-assembles): it is not a task input. Tests authenticate via the `DevAdminAuth` JUnit5 extension (`src/backend/implementation/src/test/kotlin/io/pythia/auth/DevAuthTestSupport.kt`).

**Just-in-time user provisioning**: the auth modules only populate an in-memory `CurrentUser`; a persisted `User` row is created on first sighting by `CurrentUserService.ensureUser(principal)` (keyed by the unique `entraSubjectId`). The reliable trigger is `UserProvisioningFilter` — a provider-agnostic `@Blocking` request filter (`auth/`) that provisions the current user on every authenticated **mutating** request (POST/PUT/PATCH/DELETE); `GET /api/auth/me` also provisions. This is what makes `User` FKs (audit, ownership, the undo log) resolvable. `ensureUser` takes the principal as a parameter (pure to test; no DB writes on the Vert.x event loop). Note the **dev** frontend builds its account client-side and does **not** call `/api/auth/me`, so for dev the filter — not `/me` — is what provisions users. The **Entra** frontend, however, now calls `GET /api/auth/me` on load (task-120, to read backend-authoritative roles), and `/me` provisions too — so under Entra either path provisions the user.

**Per-user language preference** (phase-16, task-123): the `users.language char(2) NOT NULL DEFAULT 'de'` column (`V12`) persists each user's UI language. `SupportedLanguage` (`io.pythia.i18n`, a `@JsExport` enum `DE`/`EN` with an ISO `code`, shared with the frontend via the `typescriptDist`) is the one canonical name both sides use; the top-level `fromCode(code)` bridges wire/DB codes to it. `ensureUser(principal, requestedLanguage? = null)` **seeds** the language on first sighting only — from the request's `Accept-Language` (`en` → `EN`, otherwise `DE`), applied by both the mutating-request `UserProvisioningFilter` and `GET /api/auth/me` — and never overwrites an existing user's stored choice. `CurrentUserService.updateLanguage(principal, language)` persists an explicit choice (`PUT /api/auth/me/language`, see `rest/CLAUDE.md`). Language lives on the `User` row, never on the token-derived `CurrentUser` principal.
