# Services: Excel/CSV import and export

Loads when working under `src/backend/implementation/src/main/kotlin/io/pythia/service/`. The backend-wide rules are in `src/backend/CLAUDE.md`.

**Export dispatches on the estimation's own method (task-107).** `GET /api/estimations/{eid}/versions/{n}/export?format=xlsx|csv` reads `estimation.method` and hands it to `CsvExporter`/`ExcelExporter`, which ask `EstimationMethodRegistry.require(method)` for the column shape — `exportColumnHeaders()` for the header and `exportRow(item)` for each leaf's cells. task-098 introduced the lookup but pinned it to `THREE_POINT_PERT`, so a bucket estimation exported PERT headers over PERT values. **Nothing may assume a column count**: PERT contributes 3 (`Min/Expected/Max`), bucket+sampled 5 (`Bucket/Is Sample/Optimistic/Likely/Pessimistic`), and three places used to hardcode 3 — a group's empty cells, a leaf's three effort cells, and the CSV totals row, which was the literal `,Total,,,,,,X,` with the total pinned at index 7. Derive all of them from `exportColumnHeaders().size`. The method columns' POSITION is frozen (CSV `Path,Group,Description,<method>,Mean,OfferPT,Node type`; xlsx `Beschreibung,<method>,…`) because `ExcelImporter` reads the structure sheet by fixed column INDEX — so the xlsx layout is a round-trip contract, and the exporter shifts every trailing index by `methodColumns.size - 3` to keep it internally consistent. `exportRow` returns strings; the xlsx writer re-parses numerics so those cells stay NUMERIC for `cellNumericValue()`. Bridging persisted node → domain item is `SubmittedItemMapper`; do NOT rebuild a method's column shape in the backend. **The xlsx round trip works for every method (task-182).** `ExcelImporter` resolves the same module from `estimation.method` and derives the same `exportColumnHeaders().size - 3` shift the exporter applies, so the two sides cannot drift; it asks `module.importRow(cells)` to read the method block rather than knowing any method's columns itself. A bucket workbook carries an **`Eimer` sheet** (label, position, id) and import matches buckets **by LABEL**, creating any that the target estimation lacks — a file's bucket ids belong to the estimation that wrote it and mean nothing elsewhere. A bucketed leaf comes back as a `DraftBucketedItemNode`; a non-sample keeps no triple, because its numbers derive from its bucket's samples and re-importing them would invent values nobody entered. The sheet is written only for `BUCKET_SAMPLED_PERT`, so a PERT workbook is unchanged. Accompanying work (`TIME_RELATIVE`) is valid in a bucket estimation too (task-187): `BucketMethodModule.exportRow` writes its triple into the method's own Optimistic/Likely/Pessimistic columns, and the importer reads it back at `METHOD_FIRST_COLUMN + module.effortColumnOffsets` — never the PERT columns 1..3, which in a bucket sheet hold Bucket / Is Sample / Optimistic. So the importer still learns no method's shape. **The import has an endpoint and a UI since task-183**: `POST /api/estimations/{eid}/versions/import/xlsx`, multipart like the Merlin import, mirroring its rules — `201` with the new draft, `404` unknown estimation, `409` when a draft already exists (the frontend opens the shared `ReplaceDraftDialog` rather than destroying it), `400` for an upload that is not a readable workbook. **A workbook whose method disagrees with the estimation's is refused with `422`, not imported.** That is the correctness point, not a nicety: `ExcelImporter` shapes its column block from `estimation.method`, so a bucket+sampled workbook (five method columns) read as PERT (three) takes every trailing value off the wrong offset and imports numbers nobody entered — silently. The file says which method wrote it, because the exporter writes the `Eimer` sheet on method alone (`if (method == BUCKET_SAMPLED_PERT)`), so its presence is an exact mirror of the check. `422` rather than a second `400` because the frontend maps the two failures to different messages BY STATUS; collapsing them leaves the user unable to tell a corrupt file from one that simply belongs elsewhere. `importXlsxDraft` therefore takes the uploaded file's `Path`, not an `InputStream` — the workbook is read twice (peek, then import) and a stream is single-pass. POI reports "not an OOXML file" as `NotOfficeXmlFileException`, which extends `IllegalArgumentException`, so the peek must catch that too or an unreadable upload escapes as a `500`.
