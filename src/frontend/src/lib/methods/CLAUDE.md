# Pluggable per-method editors

Loads when working under `src/frontend/src/lib/methods/`. The frontend-wide rules are in `src/frontend/CLAUDE.md` and the root `CLAUDE.md`'s "Frontend hard rules".

## Pluggable per-method editors

Per-method editor UIs are pluggable: `$lib/methods/registry.ts` maps each `EstimationMethod` to a lazy `import()` of `$lib/methods/<method>/EditorModule.svelte`; the version editor route reads the estimation's `method` and renders the resolved module as a dynamic component, while keeping autosave + undo/redo on the route (the module is a pure `$bindable` view). `registry.ts` also exports `availableMethods` (derived from the registered modules + a `methodLabels` map) which drives the method picker in `CreateEstimationDialog.svelte` (task-116) — registering a method there implies full-stack support.

PERT lives in `methods/pert/`; the bucket + sampled editor lives in `methods/bucketSampled/` (task-104): `EditorModule.svelte` renders the shared panels plus a `BucketPanel.svelte` (add/rename/delete/drag-reorder buckets, `svelte-dnd-action`) and a `TreeTable` of bucketed leaves (bucket picker → `bucketId`, sample toggle → `isSample`, a phase select → `phaseAbbreviation`, a three-point editor shown only on sample rows, a read-only derived `mean` column for non-sample rows, and an assumptions field). The phase and assumptions columns were missing until task-186 — the model, the database and the Excel export all carried both, so they were visible in the exported workbook and nowhere in the product. Since task-187 it also has a `type` column ("Bucket" ↔ "h/Woche"): a bucket estimation holds accompanying work too, which shows "—" for bucket and sample, always edits its own triple, needs a phase ("⚠ Phase nötig" otherwise), and is collected in its own bucket-view row "Begleitende Leistungen" (`bucket:accompanying`), never in "Ohne Bucket". "Bucket" is disabled while no bucket exists, because the backend rejects a bucketed leaf without one. What the bucket table deliberately does NOT take from the PERT grid is `pert` (replaced by `mean`, which for a non-sample is its bucket's average). The leaf selects carry `bucket.leaf-type` / `bucket.leaf-bucket` / `bucket.leaf-phase`; address them by testid, never by position — the type column shifted every positional locator once already.

Since task-132 that editor offers **two views** over the same `roots`, toggled by a segmented control (the choice persists in `localStorage` under `estimator.bucketView`; default `bucket`). They are **two projections of one model**, and their drag-and-drop meanings are deliberately disjoint: the **bucket view** renders a `$derived` synthetic tree — one row per bucket in `position` order plus a trailing `bucket:unassigned` row (which also collects leaves stranded by a deleted bucket) whose children are the *flattened* leaves of the whole tree; that unassigned row is a rescue **source only** — a drop *into* it is deliberately ignored, because the backend rejects a `BUCKETED` leaf with a null `bucketId` (`400`), so accepting it would only yield a failing autosave. A drop onto a real bucket changes **only** `bucketId` (via `onChildrenChange`, never moving anything in the real tree; ordering inside a bucket is **not persisted**, so a same-bucket reorder is a deliberate no-op). The **hierarchy view** is the real nested-group tree with `+ group` / `+ item` / `✕` row actions, where a drop restructures the tree and never touches `bucketId`. Those row actions render only on a `GROUP` row, so the view ALSO carries a **root-level `bucket.addGroupRow`** ("+ Gruppe hinzufügen") in both its footer and its empty state — without it a flat draft could never grow its first group and the view looked broken (task-150; the seeded bucket estimation was flat too, so nobody saw a group in dev). The **bucket view deliberately has no group affordance**: its rows are synthetic bucket rows, not domain groups. `e2e/bucket-hierarchy.test.ts` pins the whole loop. Bucket estimations legitimately contain `GROUP` nodes — the Merlin importer (task-131) creates exactly that shape — which the old flat editor could not display at all.

Synthetic bucket rows are **not** domain groups: they carry a synthetic `logicalId` (`bucket:<id>`) only to satisfy `TreeTable.getId`, and their numbers are a display-only **sum** of their leaves' already-computed `calcMap` entries; all bucket math stays in the domain's `BucketMethodModule`. The per-row bucket `<select>` remains in both views so re-bucketing stays keyboard-reachable. Since task-134 the bucket view opens with all **bucket rows collapsed** — expressed as `TreeTable.defaultCollapsed={isBucketRow}` (its first consumer), so every bucket is visible at once and a cross-bucket drag is a short movement. `defaultCollapsed` is a **rule, not a seed**: it is consulted for every row the user has not toggled, so a bucket added after mount starts collapsed too (it was seeded once into local state before, which both made a later-added bucket render expanded and tripped Svelte's `state_referenced_locally` warning — do not go back to copying the prop into `$state`). That collapse state is transient: it is not persisted (unlike the view choice in `localStorage`), and toggling to the hierarchy view and back remounts the table, dropping the user's overrides so the rule re-collapses the rows. The hierarchy view stays fully expanded — there the nesting is the information. The route owns a `currentBuckets` `$state` (read from the estimation-detail `buckets`, seeded XS/S/M/L/XL for a fresh draft) and PUTs it as `DraftUpdateDto.buckets`. The chosen estimation method is surfaced in the project-detail estimations table, the estimation-detail header, and the version editor header via `$lib/methods/labels.ts::formatMethodLabel` (task-118).
