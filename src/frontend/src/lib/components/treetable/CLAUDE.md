# Generic `TreeTable`

Loads when working under `src/frontend/src/lib/components/treetable/`. The frontend-wide rules are in `src/frontend/CLAUDE.md` and the root `CLAUDE.md`'s "Frontend hard rules".

## Generic `TreeTable` component

`src/frontend/src/lib/components/treetable/TreeTable.svelte` is a domain-agnostic, OmniOutliner-style tree-table component generic over a node type `T`. Callers supply `getId` / `getChildren` + a column array whose `cell` snippets render per-row content (branching on the node's data discriminator to draw editors on leaves and aggregates on group rows). The component owns indent guide lines, expand/collapse, nested per-group `svelte-dnd-action` dndzones, cycle protection (deep-clone snapshot + microtask-deferred structural-anomaly check: duplicate IDs OR lost IDs), and the header / optional footer / optional per-row actions slot. The zones use `useCursorForDetection`, so a children zone with **no** children must keep a `min-h-8`: an empty zone otherwise collapses to 0 px and can never be hovered, which silently made an empty group — and every freshly created (hence empty) bucket in the bucket view — impossible to drop into. A group's children zone is also rendered **when the row is collapsed** (task-134), because `svelte-dnd-action` captures its drop zones **at drag start** — `watchDraggedElement` instruments exactly the zones registered at that moment — so a zone that first appears mid-drag can never receive the drop. (That is why "spring-loading" a collapsed row on hover was tried, measured and rejected.) The collapsed row's descendants therefore stay in the DOM and are collapsed visually instead, via `h-0 overflow-hidden invisible` on the row wrapper — `visibility: hidden` rather than `display: none` on purpose: it keeps a layout box for the library's geometry while removing the subtree from the tab order. Because `items` and the DOM children stay one-to-one, `applyChildren` keeps its replace semantics and the cycle protection is unchanged. A collapsed zone claims its `min-h-8` strip only while a drag is in flight (`dragActive`, derived from the existing `draggedSubtreeIds`). The `roots` prop is `$bindable` so callers can run imperative add/delete mutations that the component reflects immediately. Optional `rowAttrs` and `childrenZoneAttrs` hooks let callers attach extra attributes (e.g. legacy testids, per-group aria-labels) to outer row wrappers and to children dndzones. Types live in `treetable/types.ts`.

**A cross-zone finalize publishes BOTH zones, and the anomaly checkpoint runs once (task-163).** `svelte-dnd-action` fires `finalize` on the source zone *and* the target zone for a move between zones, and `TreeTable` needs its structural-anomaly revert to run once per drag, not once per zone. That used to be expressed as an early `return` on a `cycleCheckPending` flag placed *before* `onChildrenChange` — which also swallowed the second zone's payload, so **only one half of the move was ever published**. Invisible to a consumer that re-reads `roots` (the demo harness, `EstimationGrid`), because `applyChildren` mutates the bound model for both zones regardless; fatal to one that applies the PAYLOAD, which is exactly what the bucket view's `onBucketChildrenChange` does — it takes the target bucket from `e.parentPath`. Each zone's payload is now queued in `pendingPublishes` and the whole queue is drained inside the microtask, after the anomaly check has decided whether the drag stands. **The order the two dispatches arrive in is not symmetric and is not ours to choose**: the library sends *target-then-source* for a pointer drag (`handleDrop`) but *source-then-target* for a keyboard drag, so the suppressed publish was the one carrying the move for keyboard only — a keyboard re-bucketing silently did nothing, while the same gesture with the mouse worked. Do not re-collapse the queue back to a single `onChildrenChange` call. `e2e/tree-table-dnd-mouse.test.ts`'s "cross-zone drop commits to the target zone" pins it via the demo route's `publish-log` readout, which exists for exactly this (the DOM assertions there pass either way and prove nothing about it).

Two things that were *suspected* in task-163 and are ruled out, so nobody re-derives them: the anomaly check cannot fire mid-move — both `dispatchFinalizeEvent` calls are synchronous inside one library function with no `await` between them, so the `queueMicrotask` checkpoint always observes a whole tree — and the publish fix does **not** explain the intermittent `bucket-views.test.ts` "dragged into an EMPTY bucket" failure, which is a pointer drag and therefore always received the target's payload first. That flake is **task-184**, still open: it reproduces ~1 run in 20 at `--workers=4` and never in isolation, so a green run of that spec alone means nothing. A third hypothesis is ruled out there too — the empty bucket's zone cannot be zero-height, since `min-h-8` applies unconditionally when a zone has no children (only the *collapsed non-empty* case gates on `dragActive`). The `log.debug` lines now in `handleZoneEvent` (zone key, path, child count, trigger, publish count, and the ids a revert lost) exist to diagnose it from a trace rather than by reasoning a fourth time — and note that a later run clears `test-results/`, so a failing trace must be copied out immediately.

**Production consumer**: `src/frontend/src/lib/components/EstimationGrid.svelte` (the estimation editor — composes TreeTable with 12 column snippets, calc-map aggregation, keyboard cell-nav, and the `+ group` / `+ item` / `✕` row actions. One of those columns is **not** calc-map derived: `criticalPath` (task-170) renders a `●` from a `criticalPath: ReadonlySet<string>` prop of logical ids, threaded route → method module → table. It is deliberately separate from `calcMap` — the schedule is its own computation with its own error kinds, and folding it in would make a scheduling failure look like a calculation one. The set is EMPTY whenever there is no schedule or it errored, so the column just blanks). **Regression harness**: `src/frontend/src/routes/dev/tree-table-demo/+page.svelte` (a static product-catalog fixture exercising the generic API, accessible at `/dev/tree-table-demo`).

Columns may opt in to auto-collapse on narrow containers via `collapsible: true`; the threshold is configurable per-TreeTable through `collapseBreakpointPx` (default 900 px). The outer wrapper is horizontally scrollable, so content that exceeds the viewport stays reachable even when no columns collapse further. Per-row action buttons (the `rowActions` snippet) live in a dedicated trailing column by default; callers can pass `actionsPlacement="treeColumn"` to inline the actions inside the tree column instead — EstimationGrid uses this so its `+ group` / `+ item` / `✕` controls sit directly after the row title rather than off to the right past every value column.

**A header label never paints outside its own column** (task-140): the header row (`data-testid="tt-header"`) is deliberately **normal-case** — `uppercase tracking-wide` cost ~20-25 % extra width for no legibility gain, which is what pushed labels out of their fixed tracks — and every header cell carries `min-w-0 overflow-hidden whitespace-normal break-words leading-tight`, with `items-end` on the row so a wrapped two-line label stays on the baseline of its single-line neighbours. Without that, a **single long word cannot wrap** and simply overflows its grid item, painting over the neighbouring header (DE "PESSIMISTISCH" needs ~108 px in a 6rem track's ~80 px content box). `overflow-hidden` is deliberately NOT applied to the data cells — they hold focusable `<input>`/`<select>` elements whose focus rings it would clip. `e2e/treetable-header-fit.test.ts` guards this by measuring `scrollWidth <= clientWidth` on every header cell across the PERT grid and both bucket-editor views, **in both locales** (the defect is translation-dependent, so a German-only check would let an English regression through); its first case measures `dev-admin` in the run's `E2E_LANG` and its second switches `dev-estimator` to the other language, so every run covers both. `dev-estimator` is used because the language preference is persisted per user and specs share one backend — but it is **shared** with the session and undo specs, not dedicated (see `e2e/CLAUDE.md` for the resulting race).
