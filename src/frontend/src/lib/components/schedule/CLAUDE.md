# Schedule: bridge, dependency editor, Gantt

Loads when working under `src/frontend/src/lib/components/schedule/ (and the schedule route)`. The frontend-wide rules are in `src/frontend/CLAUDE.md` and the root `CLAUDE.md`'s "Frontend hard rules".

## Schedule bridge and dependency editor (task-157)

`adapter.ts` has a **second** entry point beside `computeEstimation`'s calc map and totals — and it is the same call, not a second one. Passing the optional `scheduleInputs` (`{ dependencies, teamFte }`) makes `computeEstimation` also return a `schedule: ProjectScheduleView | null`, read off the version it has **already** built and calculated. Do not add a `computeSchedule(roots, …)`: it would rebuild and recalculate the whole estimate a second time per keystroke, which is exactly the double-compute task-139 removed.

The domain factory is `scheduleVersion(version, Array<ScheduleDependency>, teamFte)` — an `@JsExport` function taking `List<T>` is not callable from JS with a plain array, hence the Array-taking form. Coming back, `ProjectSchedule.tasks` and `ScheduleError.involvedLogicalIds` are Kotlin `List`s, read with `.asJsReadonlyArrayView()` like `calculated.roots` and a group's `children`. `ScheduledTask.parentLogicalId` is `Nullable<string>`, i.e. `string | null | undefined`, so the view normalises it with `?? null`; and `ScheduleErrorKind` crosses as an object whose `name` is the constant, not as a bare string.

`$lib/components/schedule/DependencyEditor.svelte` renders that schedule and **computes nothing** — durations, the roll-up, the critical chain and the dates all come from the domain (task-164/task-166). Only the layered layout is the component's own, and layout positions are deliberately not model data: nothing about a card's position is persisted. No charting or graph library, matching how this repo hand-rolls `TreeTable` and its drop-zone geometry.

**The three card kinds are distinguished by SURFACE and EDGE, not by a glyph (task-174).** `nodeKind(task)` yields `leaf` / `group-open` / `group-closed` and drives the class list, the `data-node-kind` attribute (the hook `e2e/schedule.test.ts` measures) and a `sr-only` span, so the three can never disagree. A leaf is plain white with an even hairline; a COLLAPSED group is tinted `bg-brand-green/5` and carries a second outline offset behind it, because it stands in for a subtree that is not on the canvas; an EXPANDED group is white with a heavier top edge and otherwise recedes, since its children are already visible inside its dashed subtree box. State stays orthogonal to kind: the critical path is line WEIGHT (`border-2`), not a colour — and the base width is emitted as EITHER `border` or `border-2`, never both, because two border-width utilities on one element leave the winner to stylesheet order. A cycle keeps its amber ring.

**What the net-plan standards do and do not give you.** DIN 69900:2009 recommends the RECTANGLE for an activity node (so the card shape is standard-conformant) and marks the critical path in red or with thicker lines (hence the weight). But DIN classifies nodes by ARROW TOPOLOGY — Start-, Ziel-, Sammel-, Verzweigungs-, Anschlussknoten — and neither it nor PMI's Precedence Diagramming Method defines a leaf-versus-summary symbol; that distinction is a WBS/Gantt concept. The group treatment above is therefore a deliberate borrowing from the Gantt summary bar, NOT standards conformance — do not add a citation for it. The DIN 3×3 node grid (Nr, Dauer, FAZ/SAZ, FEZ/SEZ, GP/FP) is a deferred option: `ScheduledTaskView` exposes only `earliestStart`/`earliestFinish`, with no latest dates or buffers to fill it.

**Canvas layer order** (four layers, and getting it from a z-index number is what broke task-167's drag arrow): the edges `<svg>` (`absolute inset-0`, NO z-index) → a collapsed group's stack outline (z-index auto, placed by DOM order immediately before its card) → the cards (`z-10`) → the live drag-arrow overlay (`z-20`).

Collapse follows the `TreeTable` shape: a **rule** consulted per node (`expanded` is a `Set` of explicitly-opened ids), never a seed copied into `$state`, so a group that appears later starts collapsed too. It is view-only and never sent to the backend. An edge whose endpoint is inside a collapsed group is drawn on the **visible ancestor** and de-duplicated, so collapsing never appears to delete a dependency.

**A cycle can no longer be DRAWN — it is refused at drop time (task-172).** `addEdge` builds the candidate edge list and asks the page's `cycleCheck` prop whether it would close a loop; a non-null answer opens `CycleRefusedDialog` (one Cancel button, no "create anyway" — a cyclic graph yields no schedule, so the override would buy nothing) and returns WITHOUT pushing, so nothing is committed, autosaved or navigated away from. The check is a **speculative `computeEstimation`** on the candidate list, owned by the schedule page and passed in as a callback: cycle detection is domain logic, and a hand-rolled traversal in the component would give WRONG answers because a drawn edge is not a graph edge — a group edge lowers to `g#start`/`g#finish` milestone nodes, so loops can exist that endpoint-to-endpoint walking misses. The callback shape is what keeps the component free of the version and still computing nothing. A self-edge routes through the same modal (it is a one-node cycle); a duplicate edge stays a silent no-op. **The CYCLE branch is retained deliberately even though normal editing can no longer reach it**: `DraftUpdateApplier.applyScheduleDependencies` stores whatever dependency rows a `PUT` sends, validating neither endpoints nor acyclicity, so a version can arrive cyclic through the API and must stay escapable. `e2e/schedule.test.ts` seeds exactly that case through the API to keep the recovery path covered.

**The CYCLE branch must render before any empty-state check.** task-155 returns an empty `tasks` list alongside the error, so an `if (tasks.length < 2)` test first would swallow the notice and tell the user there is "nothing to connect" when they have in fact just drawn a cycle — `e2e/schedule.test.ts` pins this. Errors are structured (`error.kind` is `CYCLE` or `INVALID_TEAM_FTE`) precisely so the UI maps them to `schedule.error.*` catalog keys rather than rendering a domain-composed English sentence. **That empty `tasks` list has a second consequence: the cycle notice cannot name anything through `byId`**, which is built from `schedule.tasks` — so at the one moment the user most needs to read item names (picking which dependency to delete), the schedule can supply none. Display names for those rows therefore come from the estimation TREE, through a `labels: ReadonlyMap<string, string>` prop the schedule page derives with `labelsByLogicalId` from `$lib/estimationNodes` (task-171); the rows used to render truncated logical ids for exactly this reason. `labelsByLogicalId` mirrors the domain's `labelOf` — group → `title`, leaf → `description` — and must stay in step with it, or one node gets two names. A lookup MISS renders the `schedule.editor.unknownItem` placeholder rather than an id, because a dependency can outlive the item it references: the version editor's PUT omits `dependencies`, so deleting a leaf there leaves any dependency naming it behind.

**The plan length and the uncertainty band are two different measurements and are never merged into one range.** `projectDurationDays` is the resource-levelled makespan; the optimistic…pessimistic band is estimate uncertainty along the critical chain with capacity ignored. Under task-155's old `offerPT / teamFte` formula the loaded figure sat at the top of the band, but after task-166 they are not the same scale — three independent 10-day items at `teamFte = 1` give a makespan of 30 and a band of [10, 10], outside it entirely. Label each for what it is.

The team-size field is a **worker count**: a fraction rounds down with a floor of one, which the hint states rather than applying silently.

**Accompanying work spans its phase, and cannot be depended on (task-177).** A `h/Woche` item (project management, UX support) is excluded from the schedule in the domain, so it never appears in `schedule.tasks`. Two consequences the UI relies on: `DependencyEditor` renders its cards FROM `schedule.tasks`, so such an item has no card, no drag handle and no drop target — the gesture is impossible by construction, and adding a guard there would be dead code; and `GanttChart` cannot get these items from the schedule, so the route derives them from the TREE (`variableItems`) and draws each across its phase's window from `schedule.phaseWindows`, which is what makes them parallel to everything in the phase rather than a layout special case. Their bar differs in surface AND edge (dashed outline, lighter fill), so the distinction survives without colour.

**A phase's length is per-phase EXPLICIT or AUTOMATIC.** `PhasesPanel` writes the computed weeks back when AUTOMATIC so the persisted number matches what is shown — guarded, or it would autosave on every render — and says so explicitly when an automatic phase has no scheduled work, because a variable item there computes to zero effort and a bare "0 weeks" reads as a defect. `phaseWindows` reaches the panel through both editor modules and the version-editor route.

**The plan as bars, and the Mermaid export (task-158).** `$lib/components/schedule/GanttChart.svelte` renders `ProjectScheduleView` and **computes nothing** — every offset is `earliestStart` and every length `durationDays`, as a percentage of `projectDurationDays`, so the bars are the LEVELLED plan. A group's bar is its rolled-up SPAN (`earliestFinish − earliestStart`), which deliberately does not equal the sum of its children when they overlap (task-164), and `onCriticalPath` is a critical CHAIN — a bar can be critical because the team was busy, not only because of a dependency (task-166), so never label it "longest dependency chain". Either `error.kind` replaces the chart entirely: a Gantt drawn from an empty task list would read as "zero days". It lives on the SCHEDULE route beside the graph, NOT in the version editor — task-170 removed the per-item duration list from that page on purpose, and a Gantt is one row per task.

**Working days become calendar dates in the EXPORT and nowhere else.** The domain stays in working days (task-155); the export takes a project start date from the user and walks forward skipping Saturdays and Sundays (holidays are deliberately not modelled). Do not "helpfully" move that mapping into the domain — it is a presentation concern, and it is the rule a future change is most likely to break. The export is Mermaid `gantt` TEXT downloaded as `.mmd`: diffable, and it renders natively in GitHub, GitLab and Confluence, so **no charting library is needed and none may be added** — the same reason the icon pipeline uses Playwright's bundled Chromium rather than `sharp`. It goes through `downloadResponse(...)` like every other export, never a plain `<a download>`, and its `catch` both logs via `$lib/log` and surfaces through the route's `ErrorBanner`. A unit title is free text, so `:` and newlines are stripped before they reach Mermaid syntax.

### Its own route, and one writer for `dependencies` (task-167)

The graph lives at `routes/estimations/[id]/versions/[versionNumber]/schedule/+page.svelte`, not in a panel: a net plan needs the full viewport and scrolls horizontally by layer, and an accordion three panels down is the wrong shape for a working surface. The version editor keeps the **numbers** — team size, planned length, uncertainty band — and links out to the graph. It deliberately no longer lists **per-item rows** (task-170): that table re-listed the whole estimation tree a second time on the same page and grew with it, pushing the figures and the link off screen; the one column it added that the grid lacked, `onCriticalPath`, became a grid column instead. Do not restore it as a missing feature. Per-item durations live on the graph page's cards.

That route cannot share the version editor's `$state`, so it owns its own load → edit → PUT cycle, and its PUT is a **partial `DraftUpdateDto`** carrying only `{ teamFte, dependencies }`. That is correct rather than lazy: every field there is optional and a null field means "leave unchanged" (task-156), so sending `roots` or costs from the graph page would clobber edits made in the editor.

**Only one route writes `dependencies`.** The version editor still *loads* them (its numbers are computed from them) but no longer sends them — leaving them in its autosave was a lost-update path: edit the graph, navigate back, touch any unrelated field, and the editor's stale copy wins. `teamFte` is the deliberate exception, editable in both places with last-write-wins accepted, because it is one scalar that belongs beside the numbers *and* beside the graph.

**Layout: `x` is dependency layer + depth indentation, `y` is tree order.** Row assignment walks the tree depth-first so a group's descendants occupy a contiguous band — without that, indentation and the container outline are illegible because a child can be rows away from its parent. Layer assignment is untouched, so `x` still encodes dependency order; `INDENT` is deliberately small relative to `CARD_W + GAP_X` because `x` carries both meanings and a deeply nested card must never look like it sits in the next layer. Positions are still **derived, never persisted**.

An **expanded** group draws a dashed `<rect>` (`data-testid="schedule-group-box"`) around its own card and its whole subtree. A **collapsed** one draws none — the single card already *is* the group, so a rect around one card is noise.

**The live drag arrow is driven by `dragover`, NOT `pointermove`.** The browser **suppresses pointer events for the duration of a native HTML5 drag**, so a `pointermove` handler never fires once the drag starts and the arrow stayed invisible — that was the first shipped version's bug. `dragover` fires repeatedly while the pointer crosses the canvas and carries usable `clientX/clientY`; the `drag` event on the SOURCE is the one that reports `0` in some browsers, so do not reach for that instead. Both the canvas and each card wire `ondragover` to the same handler, or the arrow freezes as soon as the pointer is over a card. Client coordinates become canvas-local via `getBoundingClientRect()`.

The DROP stays native `draggable`/`ondrop`: it has no cursor-geometry race, which is why task-157 chose it — and it is not a `svelte-dnd-action` zone at all, so neither half of task-163 (the dropped cross-zone publish, and the cursor-geometry flake still open in `bucket-views.test.ts`) can reach this component. Both committed edges and the in-flight one carry `marker-end="url(#schedule-arrow)"`, one `<marker orient="auto">` defined once in `<defs>`. **The arrowhead's angle comes from the PATH's end tangent, not from the marker** (task-175): a cubic's direction at its end is `3·(P3 − P2)`, so the original control point at the endpoint's own `y` pinned every head to 0° however correct `orient="auto"` is — the fix is upstream of the marker, and changing `orient` is a no-op. Both connectors are now built by the single `connector(x1, y1, x2, y2)` helper, which leaves the source horizontally and arrives along the chord; `path()` and `dragPath` must both keep calling it, since the duplicated curve is exactly what let the committed edge and the live arrow carry the same defect. Its `k` is clamped by `len / 2` as well as by a floor and ceiling: a committed edge always runs left-to-right (a target's layer is strictly greater than its predecessors'), but the drag endpoint is the POINTER and can sit left of the source card, where a bare floor would loop the arrow back on itself.

**A child card is never placed left of its parent.** `layer` is derived from DEPENDENCIES alone, so an undependent child of a group sitting in layer 2 would get layer 0 and land far to its parent's left, destroying the containment the outline implies. Each child's effective layer is therefore clamped to at least its parent's, and its `x` is additionally floored at `parentX + INDENT` — so `x` is monotonic down a branch by construction. Canvas width comes from the PLACED boxes rather than the raw layer map, because clamping can push a card further right than its own layer suggests. `e2e/schedule.test.ts` pins both the arrow and the nesting.

**And a GROUP starts at the layer of its earliest member** — the bottom-up half of the same rule. Layer relaxation only constrains nodes a dependency actually names, and the clamp above only propagates DOWNWARD, so a dependency between two LEAVES in different groups ordered the leaves while leaving both group cards at layer 0: they rendered as peers at the same `x`, with nothing on screen saying one group's work follows the other's (reported from the dev stack for "Benutzerkonto & Login" → "Authentifizierung & Autorisierung"). A reverse walk over `tasks` (which is in tree order, so children are visited before parents and one pass settles every depth) raises each visible group to the MINIMUM layer among its visible children. Min, not max: a group is a container, so it must start where its earliest child starts and stay at or left of all of them, which is what keeps the outline reading as containment. The collapsed case never had this problem, because `visibleAnchor` lowers the edge onto the group cards themselves and the relaxation then constrains them directly — so a fix that only looked at the collapsed view would have missed it entirely.
