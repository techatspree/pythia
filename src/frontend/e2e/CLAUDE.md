# Playwright e2e suite

Loads when working under `src/frontend/e2e/`. The frontend-wide rules are in `src/frontend/CLAUDE.md` and the root `CLAUDE.md`'s "Frontend hard rules".

## The pre-run database reset (task-176)

**The e2e suite creates a project per test and deletes none — `globalSetup` resets BEFORE a run (task-176).** Nine specs call `POST /api/projects`; one run's ~78 projects are harmless, but the SECOND run against the same stack degrades: list pages slow into 30-second `locator.click` / `focus` / `boundingBox` timeouts and `.first()` locators start resolving to the wrong row. Measured: 231 projects took the suite from 107 passed to 81 passed / 26 failed, and a fresh database restored it. `e2e/global-setup.ts` calls `DELETE /api/dev/test-data`, which is `@IfBuildProfile("dev")` so it cannot exist in a production image at all — that is why there is still no `DELETE /api/projects/{id}` on the production surface. A 404 (non-dev profile) warns and continues; an unreachable backend fails loudly, because every test is about to fail anyway.

Setup rather than teardown on purpose: a teardown never runs when a run is interrupted, which is how the accumulation built up, and it would destroy exactly the data someone wants to inspect after a failure. The keep-list is `SeededProjects.ALL`, NOT a name prefix — `endpoint-authorization.test.ts` creates a project called `EstimatorWrite` and several specs create them through the UI, so no prefix covers them. **Deletion order is load-bearing**: votes, then sessions, then projects. `EstimationSession` owns its items and participants with `cascade = ALL`, but NOT its votes (they are queried, not owned), and a vote references an item — so the session cascade deletes items out from under the votes unless the votes go first. A bulk `delete from EstimationSession` does not work either: bulk JPQL bypasses the persistence context, so no JPA cascade runs at all and `session_items` is orphaned.

Note that `%dev` uses `schema-management.strategy=drop-and-create`, so restarting the backend also wipes and re-seeds. That is why the accumulation only bites when the stack stays up across runs — which is the normal way to work.

## Playwright Page Objects and the translated-label ban (task-117/188/189)

e2e specs drive **Page Objects** in `src/frontend/e2e/pages/` — one stand-alone class per screen or modal, taking a `Page` in the constructor and exposing intent-level `async` methods, with **no shared base class** (an abstract `BasePage` with a `.page` field and generic helpers buys nothing and hides the selectors twice). Specs never reach into the DOM by a **translated label**: a label is a moving target no compiler checks, so every catalog edit would otherwise be a silent e2e break discovered only by a full suite run against a live stack.

**New `data-testid` values use `<screen>.<element>`** in dot-separated lower-kebab, English (`create-estimation.offer-input`, `undo-toolbar.undo`, `session.submit-estimate`). The ~90 pre-existing **flat-kebab** ones (`logout-button`, `tt-header`, `tt-row-*`, `schedule-card`, `language-select`, `dev-login-*`, `publish-log`, …) are deliberately **never renamed** — a tree-wide rename would rewrite `e2e/schedule.test.ts` (65 call sites) and `e2e/system-settings.test.ts` (21) for zero behavioural gain. A file mixing both spellings is correct, not sloppy. `logout-button` in particular stays because `e2e/language.test.ts` uses it as the handle for its DE/EN assertions.

**`src/frontend/eslint.config.js` enforces the ban** for `e2e/**/*.ts`, failing `:frontend:check` on `getByRole(…, { name: <literal> })` (any role), `getByText(<literal>)`, `getByLabel`/`getByPlaceholder`/`getByTitle`/`getByAltText(<literal>)`, `locator('text=…')` including the concatenated `locator('text=' + x)` form, and `{ hasText: <literal> }` — that last one is how a translated string slipped past an earlier draft of the gate. Since task-191 it also bans a literal value in a **CSS attribute selector** on a translatable attribute (`[title=…]`, `[placeholder=…]`, `[aria-label=…]`, `[alt=…]`, any operator), matched anywhere in a string or template literal because specs build selectors in constants and `page.evaluate` strings, and **`toHaveAttribute('aria-label'|'title'|'placeholder'|'alt', <string, regex or plain template literal>)`**. Four of task-190's five English-run leftovers were exactly these forms. **What makes it fail the build is `lintE2e`** (`./gradlew :frontend:lintE2e`, wired into `check`): the frontend-wide `npmLintReport` is informational and always exits 0, so before task-191 a violation only landed in `reports/eslint.json`. The gate runs every rule configured for `e2e/**`, not only the ban, and is enforceable because the e2e baseline is zero — keep it that way. What stays legal, and what the rule is deliberately written NOT to flag: **role-only** `getByRole('dialog'|'alert'|'alertdialog'|'spinbutton'|'listitem')`, which carries no translated string and is the correct accessibility-level handle; `getByText(<variable>)`, which matches test-generated DATA rather than UI chrome; the **English** `aria-label`s of the generic `treetable/TreeTable.svelte` (`"Children"`, `"Root nodes"`, `"Collapse"`, `"Expand"`), which is intentionally un-internationalised, in a selector or a `toHaveAttribute`; an attribute value **interpolated** from a template literal (`` `[title="${catalogText('bucket.dragTitle')}"]` ``); and `toHaveAttribute` on a `catalogText()`/`catalogPattern()` call or a non-translatable attribute (`data-node-kind`, `aria-current`).

**`toHaveValue(<literal>)` is deliberately NOT banned**, and is a reviewer's responsibility. Every literal use in the tree is test DATA (`'2'`, `'UM'`, `'Contoso GmbH'`), and no syntactic rule can tell those from a translated default such as the new bucket's `'Neu'` — which only the `E2E_LANG=en` run caught. A `toHaveValue` on a value the APP chose, rather than one the test typed, goes through `catalogText()`.

Two files are exempt via `ignores`, both on purpose. `e2e/pages/**` is *where* selectors are supposed to live. `e2e/language.test.ts` exists to prove `'Projekte'` → `'Projects'` and `'Abmelden'` → `'Logout'` across a language switch, so asserting translated text is its entire subject — do not "fix" it, and do not delete the exemption as an oversight. `e2e/treetable-header-fit.test.ts` also runs in both locales (task-140) but needs no exemption: it is testid-driven and measures `scrollWidth`.

**The flat-config trap, for anyone extending these rules.** ESLint flat config **replaces** a rule's options for matching files rather than merging them. The e2e block sets `no-restricted-syntax`, and the repo's raw-`fetch` ban is declared for `['**/*.ts', '**/*.svelte']` — which covers e2e. So the e2e block **re-declares the `fetch` entry verbatim**; without it the fetch ban silently stops existing across the whole e2e tree, and `e2e/global-setup.ts` has a comment relying on it. Adding an entry here means adding it to that array, never creating a second `no-restricted-syntax` block. A second trap, in the attribute-selector regex: the allowed `catalogText()` interpolation leaves a template quasi that ENDS at the opening quote (`[title="`), and a negative lookahead such as `(?!\2)` *succeeds* at end of string — so it must be written `(?!\2|$)`, or every interpolation is flagged.

Where a spec must assert a genuinely translated sentence — an error message, a status badge, a screen-reader string — it reads the expected text from the catalog by KEY through the shared `catalogText()` in `e2e/helpers.ts`, which reads the catalog of the run's `E2E_LANG` and throws on a missing key, rather than hardcoding a translation. Do not add a per-spec copy. That pins the key the code chose without pinning the wording. Numbers a spec cares about are mirrored onto data attributes instead (`data-position`/`data-total`, `data-all-agreed`, `data-selected`), because asserting only that the element is visible would pass at any value.

**A caution when adding a testid: the same control can live in two components.** The session room renders `PhaseOnePanel` or `PhaseTwoPanel`, each with its own optimistic/likely/pessimistic inputs, so both carry `session.{min,expected,max}-input`; a testid on one alone fails silently in the other phase. Conversely the estimation grid's empty-state and footer "add root group" buttons deliberately **share** `grid.add-group-row` — they never render together, and callers rely on `.first()`.

**The suite is locale-independent** (task-190), and proven so by running it in full both ways: `E2E_LANG=en npx playwright test`, then `E2E_LANG=de npx playwright test` (sequentially — one backend, one set of dev users; English first so the stack is left German). `E2E_LANG` is exported once from `e2e/helpers.ts` (default `de`, throws on anything but a supported catalog) and is the single source for the run language: `global-setup.ts` pins the three shared dev users (`dev-admin`, `dev-estimator`, `dev-viewer`) to it via `PUT /api/auth/me/language` before every run, `catalogText()` reads its catalog, and `parseNumber()` derives its group/decimal separators from `Intl`. The browser locale is deliberately NOT set anywhere — Accept-Language only seeds a user on first sighting, so it cannot re-language an existing one. Formatted numbers are asserted separator-agnostically (`/^2[.,]00$/`). The first English run caught five German literals the ESLint rule could not then see. Four — translated values inside CSS attribute selectors (`[title="…"]`, `input[placeholder="…"]`) and `toHaveAttribute('aria-label', /…/)` regexes — are now lint-caught (task-191); the fifth, a `toHaveValue` on a default label, is the one form still only the English run catches (see above). All of them go through `catalogText()`, or `catalogPattern()` for an ICU template whose `{placeholders}` a spec does not pin. `language.test.ts` and `treetable-header-fit.test.ts` set their own language by design (their subject is translation-dependent) and restore `E2E_LANG` in `afterEach`. **Known limitation:** both act as `dev-estimator`, which `session.test.ts` and `undo.test.ts` also use, so a session test running in parallel while one of them holds `dev-estimator` in a non-run language sees the wrong language. Fixing it needs a fourth dev user (a backend change); if it flakes, serialise with a Playwright `project` + `dependencies`, never with retries.
