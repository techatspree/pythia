# Estimation-method SPI

Loads when working under `src/domain/core/src/main/kotlin/io/pythia/method/`. The concrete methods live in their own Gradle projects (`src/domain/method-threepoint`, `src/domain/method-bucketsampled`); the domain-wide rules are in `src/domain/CLAUDE.md`.

## Pluggable estimation methods (SPI)

Estimation methods are pluggable behind a domain SPI in `io.pythia.method` (phase-15, planned in task-096). `EstimationMethod` is a `@JsExport` enum (`THREE_POINT_PERT`, `BUCKET_SAMPLED_PERT`); `EstimationMethodModule` is the interface each method implements — it supplies the per-leaf `calculate(item, params)` (mirroring `EstimationItem.withCalculationParameters`), a batch `calculateAll(items, params)` hook (default maps `calculate` per leaf; overridden by methods that need per-bucket context), plus the export `exportRow` / `exportColumnHeaders` shaping and its inverse `importRow(cells)` (task-182), so the SPI shapes **both directions** of the Excel trip and neither exporter nor importer learns a method's columns. `effortColumnOffsets` (task-187) says where optimistic/likely/pessimistic sit within those cells: a leaf the module does not own — accompanying work (`TIME_RELATIVE`) in a bucket estimation — is exported with its triple in exactly those columns and read back through them, so even that row needs no method-specific code in the importer. It has deliberately no default, so a new method decides its own offsets instead of silently inheriting PERT's; and `EstimationMethodRegistry` is a singleton `object` mapping enum → module (`register` / `get` / `require` / `all`, where `require` throws for an unregistered method). **One Gradle MODULE per method** (task-143, was "one Kotlin package per method") — each concrete method lives in its own `io.pythia.method.<method>` package **compiled by its own Gradle project**, so cross-method references are a compile error rather than a convention violation; all interaction goes through the SPI. Only the enum is `@JsExport`ed; the interface and registry stay domain-internal.

**The registry does NOT self-populate.** It used to install the standard methods from its own `init {}`, but that required `:domain:core` to name the concrete modules, which is exactly the cycle the module split forbids. Installation moved to `io.pythia.StandardMethods.installAll()` in the aggregator `:domain`, and each runtime bootstraps explicitly: the **backend** via `MethodRegistryBootstrap` (`@Observes StartupEvent`, mirroring `AuthProviderGuard`), **Kotlin/JS** via `DomainFactory.createVersion` (so `adapter.ts` needs no call), and **tests** by calling `installAll()` directly — or, inside a method module whose tests cannot see the aggregator, by registering their own module. Forgetting it surfaces immediately as `IllegalStateException: No estimation method module registered for …`. Three core→method references had to be inverted to make this possible: `EstimationItem` now declares `abstract val method` (so `EstimationVersion.calculate()` no longer sniffs leaf types) and `abstract val nodeTypeLabel` plus `diffFields(): List<LeafDiffField>` (so `DiffSummary` no longer branches on `BucketedEstimationItem` / `TimeRelativeEstimationItem`). `diffFields()` is `@JsExport.Ignore`d — it is a domain-internal hook, and it cannot be `internal` because its overriders live in sibling Gradle modules. For the same module-scoping reason `newId()` and `EstimationMethodRegistry.clear()` are now public rather than `internal`.
Each `EstimationMethodModule` also carries a `description: String` — a human-readable English description that the backend serialises verbatim as `EstimationDetailDto.methodDescription` and the frontend renders in `MethodDetailPopover.svelte` when the user clicks the method badge (task-119).

### Session SPI

`EstimationMethodSessionSupport` is a **second, sibling SPI** in the same package (task-105) — collaborative-session behaviour, deliberately NOT nested inside `EstimationMethodModule` (session support is inherently multi-estimator, so folding the two together would over-generalise both). It exposes `method` + `reduce(votes: List<SessionVoteInput>): SessionReduction`, and the same registry carries it via `registerSessionSupport` / `getSession` / `requireSession` (throwing, like `require`); `installStandardMethods()` registers `ThreePointSessionSupport` alongside the modules, and the test-only `clear()` empties both maps. Like `EstimationMethodModule`, it is domain-internal — not `@JsExport`ed. `ThreePointSessionSupport.reduce` **delegates** to `VoteAggregation.aggregate` rather than rehoming the math (the frontend bridge and `VoteAggregationTest` still reference it directly), so the SPI is a dispatch seam.

`SessionVoteInput` / `SessionReduction` (task-142) are the method-neutral marker interfaces that signature is built on; each method contributes its own subtypes **from its own package** (PERT: `PertVoteInput` / `PertReduction` in `…method.threepoint`; bucket+sampled: `BucketVoteInput` / `BucketSampledSessionResult` in `…method.bucketsampled`, task-106).

Bucket+sampled sessions vote on a **bucket assignment**, reduced per item by `reduceBucketSampledSession` with **last-write-wins plus provenance**: each estimator's most recent write wins over their earlier ones, then the most recent across estimators wins overall, and every *differing* loser is kept in `AssignmentResult.conflictingAssignments` so the UI can surface the disagreement rather than silently resolving it (agreeing on the same bucket is not a conflict). Ties on the timestamp break on `estimatorId` — a bare `maxByOrNull { it.at }` would depend on list order and make the reducer non-deterministic. Cast samples are averaged element-wise. The reducer deliberately does **not** compute per-bucket means: it decides each item's bucket and sample triple, those are written back onto the draft leaf at finalize, and `EstimationVersion.calculate()` then applies `computeBucketAverages` as usual — computing them here as well would duplicate that reducer. `EstimatorBucketAssignment.at` is `kotlinx.datetime.Instant` (JVM-only `java.time` would compile and pass `jvmTest`, then break the Kotlin/JS build), which is why `kotlinx-datetime` is an `api` dependency of `:domain:method-bucketsampled` and the aggregator — the backend maps its own `java.time.Instant` into it at the service boundary, using `updatedAt ?: createdAt` so a re-vote wins the race it should.

Two decisions there are deliberate and load-bearing. **They are not type parameters** (`EstimationMethodSessionSupport<I, R>`): the registry keeps every support in one `Map<EstimationMethod, EstimationMethodSessionSupport>`, so a generic interface erases to `*` in that map and `requireSession(...)` would return a star-projected type, forcing an unchecked cast at every call site. **They are also not `sealed`**, which would otherwise be the natural way to get an exhaustive `when`: Kotlin requires a sealed type's direct subtypes to live in the *same package*, which is mutually exclusive with the one-package-per-method rule above — declaring them in a method package fails to compile outright ("A class can only extend a sealed class or interface declared in the same package"). Exhaustiveness is replaced by the contract that `reduce` must `error(…)` on an input subtype it does not handle. `EstimatorVote` / `VoteAggregate` are **wrapped** by the PERT subtypes rather than implementing the markers directly, because they are `@JsExport`ed and reach the frontend through `DomainFactory.aggregateVotes` — giving them a domain-internal supertype would perturb the generated `domain.d.mts` surface for no gain.

### Method #1 — three-point PERT

`ThreePointMethodModule` in `io.pythia.method.threepoint` (task-098) wraps the existing per-leaf PERT calc and owns the PERT export column shape (`exportColumnHeaders` = `Min/Expected/Max`, in English); both the CSV and Excel exporters source their input-column headers from it, so the module is the single source of the PERT column shape.

**`EstimationItem` is `abstract` (task-113), so each method owns its leaf type in its own package.** `EstimationNode` stays `sealed` (its direct subclasses `EstimationGroup` + `EstimationItem` remain in `io.pythia.model`, keeping `EstimationNode.leaves()` exhaustive), but the concrete leaf types live under their method: PERT's `FixedEstimationItem` / `TimeRelativeEstimationItem` are in `io.pythia.method.threepoint` (the latter's mean scales by `phase.durationWeeks`), and task-102's `BucketedEstimationItem` lands in `io.pythia.method.bucketsampled`. Because `EstimationItem` is no longer sealed, the domain→submitted `when` in `EstimationVersionService` has an explicit `else -> error(…)` for unhandled leaf types. Registry-driven export dispatch by `estimation.method` lands in task-107.

### Method #2 — bucket + sampled PERT

`BucketMethodModule` / `BucketedEstimationItem` in `io.pythia.method.bucketsampled` (task-102). A `BucketedEstimationItem` belongs to a bucket (`bucketId`) and is either a **sample** — carrying its own `optimistic`/`likely`/`pessimistic` three-point estimate, from which `mean`/`variance`/`offerPT` derive by the usual PERT formula — or a **non-sample**, whose neutral values are the per-bucket average of that bucket's samples. Because a single leaf can't see its bucket siblings, the module overrides the SPI's `calculateAll(items, params)`: `computeBucketAverages(items, params)` averages each bucket's samples once, then `withCalculatedFromBucket(mean, variance, offerPT)` stamps those onto the non-sample leaves (`cost`/`offerPrice` derive from `offerPT` via the inherited getters). Like every other leaf it carries `assumptions` and a `phase`, and `diffFields()` reports both after its own inputs (task-186 — it forwarded a hardcoded `""` for assumptions until then, so the field was permanently empty on both platforms). `EstimationVersion.calculate()` dispatches through this batch hook — it detects the method from the leaf types (any `BucketedEstimationItem` → `BUCKET_SAMPLED_PERT`, else `THREE_POINT_PERT`), runs `calculateAll` over the flat leaves, and substitutes the calculated leaves back into the tree by `logicalId` before the group accumulation; the PERT path stays byte-identical because its default `calculateAll` is per-leaf. This adds a `model → method` reference (`EstimationVersion` → `EstimationMethodRegistry`), which is acceptable (consistent with `DomainFactory`) and is NOT a method-to-method reference.
