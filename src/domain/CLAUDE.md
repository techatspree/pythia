# Domain (`src/domain`) — Kotlin Multiplatform

Loaded when working under `src/domain/`. The module split and the `api(...)` dependency rule are in the root `CLAUDE.md`; this file is the model detail.

**The estimation-method SPI** (`EstimationMethodModule`, the registry and its explicit bootstrap, the Session SPI, both concrete methods) is documented beside the SPI in `core/src/main/kotlin/io/pythia/method/CLAUDE.md`, which loads when you work there. Read it before adding a method or changing how one is dispatched.

## Logging

Use the `io.github.oshai:kotlin-logging` facade — `private val logger = KotlinLogging.logger {}` and the lambda form `logger.debug { "…" }` (allocation-free when the level is off). On the JVM target it delegates to slf4j (the backend supplies a provider via Quarkus' JBoss LogManager bridge; the domain's own JVM tests pull `slf4j-simple` as `runtimeOnly`); on the JS target it writes to the browser console, so the frontend sees domain logs in dev. Logging is observation only — never control flow; the business math stays the single source of truth.

**Holds all business logic** — PERT calculation, accumulation, the tree-shape domain model. The backend and frontend MUST NOT reimplement domain rules; they call into it.

## Domain model: trees, not flat groups

The estimation hierarchy is an **arbitrary-depth tree**. Sealed hierarchy in `src/domain/core/src/main/kotlin/io/pythia/model/`: `EstimationNode` is `sealed`, with `EstimationGroup` (interior node — title + `List<EstimationNode>` children, accumulating mean/variance/offerPT/cost/offerPrice over its subtree via `get() = children.sumOf { … }`) and `EstimationItem` (the leaf, carrying the raw values) as its two direct subclasses.

`EstimationVersion.roots: List<EstimationNode>` is the tree root. `EstimationVersion.calculate()` flattens leaves, computes the risk factor + driver factor + daily rate, builds `CalculationParameters`, then maps the tree via `withCalculationParameters(...)`. Groups derive their numbers from children — never store accumulated values on `EstimationGroup`.

A `leaves()` extension on `EstimationNode` flat-walks the tree and returns the leaf items.

## Hardwired calculation inputs

The three calculation inputs — **`dailyRate`, `stdDevFactor`, `salesSurcharge`** — are typed `Double` **fields**, not generic name/value rows (task-138). They used to be a `List<EstimationParameter>` that `EstimationVersion.calculate()` looked up by the literal English strings `"dailyRate"`/`"stdDevFactor"`/`"salesSurcharge"`; because the GUI let the user edit the parameter NAME, a rename made the lookup miss and the estimate **silently fell back to the default** — a wrong number with no error anywhere. Typed fields make that unrepresentable, and they are what let the parameter panel be internationalised (a label is now an i18n key, not the lookup key).

So: **do not reintroduce a generic parameter collection.** `EstimationParameter`, `DraftEstimationParameter` and `SubmittedEstimationParameter` are deleted; the `draft_estimation_parameters` / `submitted_estimation_parameters` tables were folded into `daily_rate` / `std_dev_factor` / `sales_surcharge` columns on both version tables by `V16` (which back-fills each row from its old parameter rows before dropping them, defaulting anything absent). `DraftUpdateDto` carries the three as flat optional fields (`dailyRate?`, …) applied by direct assignment in `DraftUpdateApplier`, and `VersionComparisonService` still emits `ParameterChangeDto` — its `name` is now the fixed FIELD name, which the compare page maps straight onto the `panel.parameters.<name>` i18n label.

Their default values live in **one** place, the `@JsExport`ed `EstimationDefaults` object in the domain (`io.pythia.model`): the domain constructor defaults, the JPA column defaults on `DraftEstimationVersion`/`SubmittedEstimationVersion`, and the frontend `ParametersPanel`'s "use defaults" button all read it (the frontend via `EstimationDefaults.getInstance().DAILY_RATE`). Do not re-hardcode `800.0` / `2.0` / `0.1` anywhere.

## Project schedule and critical path (task-155)

`EstimationVersion.schedule(dependencies, teamFte)` turns an estimate into a rough schedule: `ProjectSchedule` / `ScheduledTask` / `ScheduleDependency` in `src/domain/core/src/main/kotlin/io/pythia/model/ProjectSchedule.kt`. Like `totals()` it is deliberately a **member and not an extension** — `@JsExport` does not export extension functions, so an extension would compile, pass `:domain:build`, and then be missing from the frontend's `domain.d.mts` — and like `totals()` it must be called on the result of `calculate()`, since a node's `offerPT` derives from the `CalculationParameters` that `calculate()` stamps on.

**Every node is scheduled, and a group is a ROLL-UP (task-164 — this supersedes task-155's roots-only rule; do not follow that one).** Leaves are the atomic units; a group is never scheduled itself, its `earliestStart`/`earliestFinish` are the min/max over its subtree leaves, and it is `onCriticalPath` when any leaf beneath it is. That is what makes "any node is schedulable" safe: a group is not in the graph, so it can never double-count its own children's effort. Roots-only was abandoned because `MerlinImporter` reconstructs a whole WBS as nested groups — an import with one top-level activity collapsed to a single unit with nothing to connect, which is the tool's main input.

A group's `durationDays` is therefore its **span** (`earliestFinish - earliestStart`), deliberately not an effort quotient: the two differ whenever children overlap, and reporting the effort-derived number on a summary row is how a Gantt gets bars that do not match their children. Durations are **working days**; calendar mapping (weekends) belongs to the export, never to the domain.

**`teamFte` is a WORKER COUNT, and the schedule is RESOURCE-LEVELLED (task-166 — this supersedes task-155's `offerPT / teamFte` formula and task-164's inherited version of it).** A leaf takes its `effortPT` in **days**, worked by one person; `slots = max(1, floor(teamFte))` items run at once, so a fractional team rounds down with a floor of one. Placement is **serial schedule generation**: each node starts at the later of its dependencies being met and a worker being free, then occupies that worker. Capacity is never exceeded by construction. **The levelling priority is the TREE ORDER (task-211):** when more nodes are ready than workers are free, the one earliest in the depth-first tree goes first (a group's two milestones take the group's rank), and ties on worker-free time resolve to the lowest slot index. It used to be the sorted `logicalId`, so the plan depended on random ids nobody chose and two identical estimates could get different schedules. Now relabelling ids changes nothing, while reordering items can change a capacity-bound plan, by design. The ready set is a plain list scanned for its minimum: `:domain:core` compiles to Kotlin/JS, where the JVM's priority-queue and sorted-set types do not exist.

Before this the code divided by `teamFte` per item but placed every item at `max(predecessor finish)` with no capacity check — so N overlapping items consumed N × `teamFte` and the plan silently cloned the team. The committed test that asserted 15 days for 25 person-days at one worker is now the regression guard for it.

**Group milestones consume no worker.** The `#start`/`#finish` nodes are flagged `isMilestone` on the graph rather than inferred from a zero duration — a real leaf may legitimately have zero effort — and they respect their predecessors while occupying nobody.

`onCriticalPath` therefore means a **critical chain**: a node can be critical because the team was busy, not only because a predecessor was. The exported field keeps its name (renaming it is a `@JsExport` surface change for no behavioural gain); only the docs and the UI wording say "chain".

**One person per item.** A 100 PT leaf is 100 days and cannot be shortened by adding people, because there is no per-item resource assignment. That is a stated limitation, and arguably useful feedback that the item needs breaking down.

Edges may name **any** node and are lowered through two zero-duration **milestones** per group (`g#start`, `g#finish`): each child is bracketed between its parent's milestones, and a drawn `A → B` becomes `finishOf(A) → startOf(B)`. That is O(nodes) edges rather than the O(leaves²) of a cross product — 102 instead of 2500 for two 50-leaf groups — and it keeps the constraint in the graph before the topological sort, which "start after A's latest finish" could not. Milestones are internal: they never appear in `ProjectSchedule.tasks`. A cycle is reported in the ids the **user drew** (group ids included), never the lowered milestones or leaves they never touched.

`ProjectSchedule.tasks` is a **flat list covering every node**, carrying `parentLogicalId`, `depth` and `isGroup`, emitted in **tree order** (depth-first, root order). Flat rather than nested because an `@JsExport`ed recursive data class reaches JavaScript as nested Kotlin `List`s that every consumer must walk; the ordering is a contract — task-157 and task-158 rebuild the tree from it without sorting.

The calculation is **method-neutral and therefore lives in `:domain:core`**, the parent both method modules depend on. It reads only `roots`, `offerPT`, `mean`, `variance` and the group title / leaf description — all declared abstractly on `EstimationNode` — so nothing distinguishes three-point PERT from bucket+sampled. That placement is self-enforcing: core declares no `project(...)` dependency, so a method-specific import there is an "Unresolved reference". **Do not add a third SPI** beside `EstimationMethodModule` and `EstimationMethodSessionSupport` — there is no method-specific behaviour to dispatch on. Its test is the one exception and lives in the aggregator `:domain` (beside `EstimationTotalsTest`), because asserting a real duration needs a concrete leaf type that core cannot see.

The project length is a **range**, not one number, and the band is built on the unloaded **mean** scale: `expectedDurationDays` sums `mean` along the longest path, `durationStdDevDays` is `sqrt(summed variance)`, and the optimistic/pessimistic ends are ± `version.stdDevFactor` standard deviations (the same knob that drives the risk surcharge). Do **not** band around `projectDurationDays`: `offerPT` already contains the risk surcharge, and that surcharge IS a standard-deviation loading (`riskFactor = sqrt(totalVariance) * stdDevFactor / totalMean`), so `± stdDevFactor * sigma` on top applies the same sigma twice. `projectDurationDays` therefore sits at the **top** of the band by construction, never at its midpoint. Two implementation traps the tests pin: variances add along a path while standard deviations do not, and the band does **not** scale with team size — since task-166 a leaf's duration is its effort in days, so the band is already in days and dividing by `teamFte` would report it that many times too small. The forward pass accumulates mean and variance from whichever predecessor won on **`dependencyFinish`** — the finish ignoring capacity — so the band still describes the longest logical path rather than whichever node the worker queue happened to delay longest, and two parallel critical branches never sum their variances.

Failures are **data**: `ProjectSchedule.error` is a `ScheduleError` carrying a `ScheduleErrorKind` (`CYCLE` / `INVALID_TEAM_FTE`) plus the `logicalId`s involved, not an English sentence — a message composed in the domain could not go through the frontend's i18n catalogs. A cycle (including a self-edge) and a non-positive `teamFte` are reported this way with an empty `tasks`, never thrown; an edge naming a deleted root is ignored, and duplicate edges are deduped.

## Accompanying work (task-177, task-213)

**Accompanying work is EXCLUDED from the schedule, and that breaks a cycle (task-177).** `TimeRelativeEstimationItem.mean` is `PERT(min, exp, max) × phase.durationWeeks` — its effort is DERIVED FROM its phase's length. So if a phase's length is computed from the plan and the plan schedules the item, the plan depends on a number that depends on the plan. The resolution is that such a leaf is not a node in the scheduling graph at all: `EstimationItem` declares `abstract val isScheduled: Boolean`, `TimeRelativeEstimationItem` overrides it to `false`, and `ProjectSchedule` filters on it. Excluded, NOT zero-length — a zero-length node would still sit in the graph and in the makespan arithmetic. The pipeline is then acyclic: schedule the scheduled leaves → `phaseWindows` → an AUTOMATIC phase length → the variable item's effort. Edges naming an excluded leaf are dropped when lowering, so a row already in the database cannot break the plan.

**Unit of accompanying work (task-213): the inputs are HOURS per week.** `TimeRelativeEstimationItem.mean` is `PERT(min, exp, max) × durationWeeks ÷ hoursPerDay` and its variance is divided by `hoursPerDay²`. Before task-213 nothing converted, so hours were summed as person-days (8× too much at 8 h/day). `hoursPerDay` is a per-installation setting (default `EstimationDefaults.HOURS_PER_DAY = 8.0`), supplied by the caller as `EstimationVersion.hoursPerDay` and carried to the leaves in `CalculationParameters.hoursPerDay`. **The trap:** `calculate()` sums the leaves' mean and variance into the risk factor BEFORE the full parameters exist, and core cannot see the time-relative leaf type — so it first stamps every leaf with `CalculationParameters(hoursPerDay = …)`, then computes totals and risk factor, then stamps the full parameters. Without that pre-stamp the risk factor silently uses 8 while the leaves use the tenant's value; `EstimationVersionHoursPerDayTest` (6 h/day) fails if it is ever removed. `DomainFactory.createVersion` takes `hoursPerDay` as its LAST parameter because `adapter.ts` calls it positionally.

`isScheduled` is abstract for the same reason `method` and `nodeTypeLabel` are (task-143): `ProjectSchedule` lives in `:domain:core`, `TimeRelativeEstimationItem` in `:domain:method-threepoint`, and a core→method import is an "Unresolved reference", not a review comment. **`WORKING_DAYS_PER_WEEK = 5.0` is the one conversion constant** — a second copy is how two parts of a plan start disagreeing.

**A scheduled leaf must carry its phase, or `phaseWindows` has nothing to group by.** The JVM path always did this (`DraftVersionMapper` builds a phase map), but `createFixedItem` took no phase, so a leaf built through the frontend adapter silently lost it and every window came back empty. The factory now takes a trailing, defaulted `phase` and `adapter.ts` passes it — if you add another leaf factory, give it a phase too.

## Kotlin/JS output granularity

**Kotlin/JS granularity is pinned to `whole-program`** (`kotlin.js.ir.output.granularity` in `gradle.properties`). The default `per-module` emits one `.mjs` per Gradle project, which split the runtime exports across `domain.mjs` / `pythia-domain-core.mjs` / … while Kotlin still wrote **all** TypeScript declarations into the single `domain.d.mts`. The frontend then type-checked fine and failed at bundle time with `"EffortDriver" is not exported by "src/lib/domain/domain.mjs"`. `whole-program` merges everything back into one `domain.mjs`, so the frontend keeps its single import site and `src/frontend/src/` needed no change at all; total shipped JS is unchanged (~338 KB, the stdlib is now inlined rather than a sibling file). Do not switch this back.
