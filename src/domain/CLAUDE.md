# Domain (`src/domain`) — Kotlin Multiplatform

Loaded when working under `src/domain/`. The module split and the `api(...)` dependency rule are in the root `CLAUDE.md`; this file is the model and SPI detail.

## Logging

Use the `io.github.oshai:kotlin-logging` facade — `private val logger = KotlinLogging.logger {}` and the lambda form `logger.debug { "…" }` (allocation-free when the level is off). On the JVM target it delegates to slf4j (the backend supplies a provider via Quarkus' JBoss LogManager bridge; the domain's own JVM tests pull `slf4j-simple` as `runtimeOnly`); on the JS target it writes to the browser console, so the frontend sees domain logs in dev. Logging is observation only — never control flow; the business math stays the single source of truth.

**Holds all business logic** — PERT calculation, accumulation, the tree-shape domain model. The backend and frontend MUST NOT reimplement domain rules; they call into it.

## Domain model: trees, not flat groups

The estimation hierarchy is an **arbitrary-depth tree**. Sealed hierarchy in `src/domain/core/src/main/kotlin/io/pythia/model/`: `EstimationNode` is `sealed`, with `EstimationGroup` (interior node — title + `List<EstimationNode>` children, accumulating mean/variance/offerPT/cost/offerPrice over its subtree via `get() = children.sumOf { … }`) and `EstimationItem` (the leaf, carrying the raw values) as its two direct subclasses.

`EstimationVersion.roots: List<EstimationNode>` is the tree root. `EstimationVersion.calculate()` flattens leaves, computes the risk factor + driver factor + daily rate, builds `CalculationParameters`, then maps the tree via `withCalculationParameters(...)`. Groups derive their numbers from children — never store accumulated values on `EstimationGroup`.

A `leaves()` extension on `EstimationNode` flat-walks the tree and returns the leaf items.

## Hardwired calculation inputs

The three calculation inputs — **`dailyRate`, `stdDevFactor`, `salesSurcharge`** — are typed `Double` **fields**, not generic name/value rows (task-138). They used to be a `List<EstimationParameter>` that `EstimationVersion.calculate()` looked up by the literal English strings `"dailyRate"`/`"stdDevFactor"`/`"salesSurcharge"`; because the GUI let the user edit the parameter NAME, a rename made the lookup miss and the estimate **silently fell back to the default** — a wrong number with no error anywhere. Typed fields make that unrepresentable, and they are what let the parameter panel be internationalised (a label is now an i18n key, not the lookup key).

So: **do not reintroduce a generic parameter collection.** `EstimationParameter`, `DraftEstimationParameter` and `SubmittedEstimationParameter` are deleted; the `draft_estimation_parameters` / `submitted_estimation_parameters` tables were folded into `daily_rate` / `std_dev_factor` / `sales_surcharge` columns on both version tables by `V16` (which back-fills each row from its old parameter rows before dropping them, defaulting anything absent). `DraftUpdateDto` carries the three as flat optional fields (`dailyRate?`, …) applied by direct assignment in `DraftUpdateApplier`, and `VersionComparisonService` still emits `ParameterChangeDto` — its `name` is now the fixed FIELD name, which the compare page maps straight onto the `panel.parameters.<name>` i18n label.

Their default values live in **one** place, the `@JsExport`ed `EstimationDefaults` object in the domain (`io.pythia.model`): the domain constructor defaults, the JPA column defaults on `DraftEstimationVersion`/`SubmittedEstimationVersion`, and the frontend `ParametersPanel`'s "use defaults" button all read it (the frontend via `EstimationDefaults.getInstance().DAILY_RATE`). Do not re-hardcode `800.0` / `2.0` / `0.1` anywhere.

## Project schedule and critical path (task-155)

`EstimationVersion.schedule(dependencies, teamFte)` turns an estimate into a rough schedule: `ProjectSchedule` / `ScheduledTask` / `ScheduleDependency` in `src/domain/core/src/main/kotlin/io/pythia/model/ProjectSchedule.kt`. Like `totals()` it is deliberately a **member and not an extension** — `@JsExport` does not export extension functions, so an extension would compile, pass `:domain:build`, and then be missing from the frontend's `domain.d.mts` — and like `totals()` it must be called on the result of `calculate()`, since a node's `offerPT` derives from the `CalculationParameters` that `calculate()` stamps on.

The scheduling units are exactly the **root nodes** (`EstimationVersion.roots`), one per root, group or leaf. Not the leaves: a dependency editor over every leaf of a 200-item tree is unusable, and a group already contributes its whole subtree through `offerPT`, so the schedule never re-derives estimation math. There is deliberately no "scheduling level" setting. Durations are **working days** — `offerPT / teamFte`, which models a team working on one unit at a time, so parallel branches come out optimistic; calendar mapping (weekends) belongs to the export, never to the domain.

The calculation is **method-neutral and therefore lives in `:domain:core`**, the parent both method modules depend on. It reads only `roots`, `offerPT`, `mean`, `variance` and the group title / leaf description — all declared abstractly on `EstimationNode` — so nothing distinguishes three-point PERT from bucket+sampled. That placement is self-enforcing: core declares no `project(...)` dependency, so a method-specific import there is an "Unresolved reference". **Do not add a third SPI** beside `EstimationMethodModule` and `EstimationMethodSessionSupport` — there is no method-specific behaviour to dispatch on. Its test is the one exception and lives in the aggregator `:domain` (beside `EstimationTotalsTest`), because asserting a real duration needs a concrete leaf type that core cannot see.

The project length is a **range**, not one number, and the band is built on the unloaded **mean** scale: `expectedDurationDays` sums `mean` along the longest path, `durationStdDevDays` is `sqrt(summed variance) / teamFte`, and the optimistic/pessimistic ends are ± `version.stdDevFactor` standard deviations (the same knob that drives the risk surcharge). Do **not** band around `projectDurationDays`: `offerPT` already contains the risk surcharge, and that surcharge IS a standard-deviation loading (`riskFactor = sqrt(totalVariance) * stdDevFactor / totalMean`), so `± stdDevFactor * sigma` on top applies the same sigma twice. `projectDurationDays` therefore sits at the **top** of the band by construction, never at its midpoint. Two implementation traps the tests pin: variances add along a path while standard deviations do not, and effort variance is in PT-squared so converting it to days divides by `teamFte` **squared**. The forward pass accumulates mean and variance from whichever predecessor won the `max`, which is also what keeps two parallel critical branches from summing their variances.

Failures are **data**: `ProjectSchedule.error` is a `ScheduleError` carrying a `ScheduleErrorKind` (`CYCLE` / `INVALID_TEAM_FTE`) plus the `logicalId`s involved, not an English sentence — a message composed in the domain could not go through the frontend's i18n catalogs. A cycle (including a self-edge) and a non-positive `teamFte` are reported this way with an empty `tasks`, never thrown; an edge naming a deleted root is ignored, and duplicate edges are deduped.

## Pluggable estimation methods (SPI)

Estimation methods are pluggable behind a domain SPI in `io.pythia.method` (phase-15, planned in task-096). `EstimationMethod` is a `@JsExport` enum (`THREE_POINT_PERT`, `BUCKET_SAMPLED_PERT`); `EstimationMethodModule` is the interface each method implements — it supplies the per-leaf `calculate(item, params)` (mirroring `EstimationItem.withCalculationParameters`), a batch `calculateAll(items, params)` hook (default maps `calculate` per leaf; overridden by methods that need per-bucket context), plus the export `exportRow` / `exportColumnHeaders` shaping; and `EstimationMethodRegistry` is a singleton `object` mapping enum → module (`register` / `get` / `require` / `all`, where `require` throws for an unregistered method). **One Gradle MODULE per method** (task-143, was "one Kotlin package per method") — each concrete method lives in its own `io.pythia.method.<method>` package **compiled by its own Gradle project**, so cross-method references are a compile error rather than a convention violation; all interaction goes through the SPI. Only the enum is `@JsExport`ed; the interface and registry stay domain-internal.

**The registry does NOT self-populate.** It used to install the standard methods from its own `init {}`, but that required `:domain:core` to name the concrete modules, which is exactly the cycle the module split forbids. Installation moved to `io.pythia.StandardMethods.installAll()` in the aggregator `:domain`, and each runtime bootstraps explicitly: the **backend** via `MethodRegistryBootstrap` (`@Observes StartupEvent`, mirroring `AuthProviderGuard`), **Kotlin/JS** via `DomainFactory.createVersion` (so `adapter.ts` needs no call), and **tests** by calling `installAll()` directly — or, inside a method module whose tests cannot see the aggregator, by registering their own module. Forgetting it surfaces immediately as `IllegalStateException: No estimation method module registered for …`. Three core→method references had to be inverted to make this possible: `EstimationItem` now declares `abstract val method` (so `EstimationVersion.calculate()` no longer sniffs leaf types) and `abstract val nodeTypeLabel` plus `diffFields(): List<LeafDiffField>` (so `DiffSummary` no longer branches on `BucketedEstimationItem` / `TimeRelativeEstimationItem`). `diffFields()` is `@JsExport.Ignore`d — it is a domain-internal hook, and it cannot be `internal` because its overriders live in sibling Gradle modules. For the same module-scoping reason `newId()` and `EstimationMethodRegistry.clear()` are now public rather than `internal`.

**Kotlin/JS granularity is pinned to `whole-program`** (`kotlin.js.ir.output.granularity` in `gradle.properties`). The default `per-module` emits one `.mjs` per Gradle project, which split the runtime exports across `domain.mjs` / `pythia-domain-core.mjs` / … while Kotlin still wrote **all** TypeScript declarations into the single `domain.d.mts`. The frontend then type-checked fine and failed at bundle time with `"EffortDriver" is not exported by "src/lib/domain/domain.mjs"`. `whole-program` merges everything back into one `domain.mjs`, so the frontend keeps its single import site and `src/frontend/src/` needed no change at all; total shipped JS is unchanged (~338 KB, the stdlib is now inlined rather than a sibling file). Do not switch this back. Each `EstimationMethodModule` also carries a `description: String` — a human-readable English description that the backend serialises verbatim as `EstimationDetailDto.methodDescription` and the frontend renders in `MethodDetailPopover.svelte` when the user clicks the method badge (task-119).

### Session SPI

`EstimationMethodSessionSupport` is a **second, sibling SPI** in the same package (task-105) — collaborative-session behaviour, deliberately NOT nested inside `EstimationMethodModule` (session support is inherently multi-estimator, so folding the two together would over-generalise both). It exposes `method` + `reduce(votes: List<SessionVoteInput>): SessionReduction`, and the same registry carries it via `registerSessionSupport` / `getSession` / `requireSession` (throwing, like `require`); `installStandardMethods()` registers `ThreePointSessionSupport` alongside the modules, and the test-only `clear()` empties both maps. Like `EstimationMethodModule`, it is domain-internal — not `@JsExport`ed. `ThreePointSessionSupport.reduce` **delegates** to `VoteAggregation.aggregate` rather than rehoming the math (the frontend bridge and `VoteAggregationTest` still reference it directly), so the SPI is a dispatch seam.

`SessionVoteInput` / `SessionReduction` (task-142) are the method-neutral marker interfaces that signature is built on; each method contributes its own subtypes **from its own package** (PERT: `PertVoteInput` / `PertReduction` in `…method.threepoint`; bucket+sampled: `BucketVoteInput` / `BucketSampledSessionResult` in `…method.bucketsampled`, task-106).

Bucket+sampled sessions vote on a **bucket assignment**, reduced per item by `reduceBucketSampledSession` with **last-write-wins plus provenance**: each estimator's most recent write wins over their earlier ones, then the most recent across estimators wins overall, and every *differing* loser is kept in `AssignmentResult.conflictingAssignments` so the UI can surface the disagreement rather than silently resolving it (agreeing on the same bucket is not a conflict). Ties on the timestamp break on `estimatorId` — a bare `maxByOrNull { it.at }` would depend on list order and make the reducer non-deterministic. Cast samples are averaged element-wise. The reducer deliberately does **not** compute per-bucket means: it decides each item's bucket and sample triple, those are written back onto the draft leaf at finalize, and `EstimationVersion.calculate()` then applies `computeBucketAverages` as usual — computing them here as well would duplicate that reducer. `EstimatorBucketAssignment.at` is `kotlinx.datetime.Instant` (JVM-only `java.time` would compile and pass `jvmTest`, then break the Kotlin/JS build), which is why `kotlinx-datetime` is an `api` dependency of `:domain:method-bucketsampled` and the aggregator — the backend maps its own `java.time.Instant` into it at the service boundary, using `updatedAt ?: createdAt` so a re-vote wins the race it should.

Two decisions there are deliberate and load-bearing. **They are not type parameters** (`EstimationMethodSessionSupport<I, R>`): the registry keeps every support in one `Map<EstimationMethod, EstimationMethodSessionSupport>`, so a generic interface erases to `*` in that map and `requireSession(...)` would return a star-projected type, forcing an unchecked cast at every call site. **They are also not `sealed`**, which would otherwise be the natural way to get an exhaustive `when`: Kotlin requires a sealed type's direct subtypes to live in the *same package*, which is mutually exclusive with the one-package-per-method rule above — declaring them in a method package fails to compile outright ("A class can only extend a sealed class or interface declared in the same package"). Exhaustiveness is replaced by the contract that `reduce` must `error(…)` on an input subtype it does not handle. `EstimatorVote` / `VoteAggregate` are **wrapped** by the PERT subtypes rather than implementing the markers directly, because they are `@JsExport`ed and reach the frontend through `DomainFactory.aggregateVotes` — giving them a domain-internal supertype would perturb the generated `domain.d.mts` surface for no gain.

### Method #1 — three-point PERT

`ThreePointMethodModule` in `io.pythia.method.threepoint` (task-098) wraps the existing per-leaf PERT calc and owns the PERT export column shape (`exportColumnHeaders` = `Min/Expected/Max`, in English); both the CSV and Excel exporters source their input-column headers from it, so the module is the single source of the PERT column shape.

**`EstimationItem` is `abstract` (task-113), so each method owns its leaf type in its own package.** `EstimationNode` stays `sealed` (its direct subclasses `EstimationGroup` + `EstimationItem` remain in `io.pythia.model`, keeping `EstimationNode.leaves()` exhaustive), but the concrete leaf types live under their method: PERT's `FixedEstimationItem` / `TimeRelativeEstimationItem` are in `io.pythia.method.threepoint` (the latter's mean scales by `phase.durationWeeks`), and task-102's `BucketedEstimationItem` lands in `io.pythia.method.bucketsampled`. Because `EstimationItem` is no longer sealed, the domain→submitted `when` in `EstimationVersionService` has an explicit `else -> error(…)` for unhandled leaf types. Registry-driven export dispatch by `estimation.method` lands in task-107.

### Method #2 — bucket + sampled PERT

`BucketMethodModule` / `BucketedEstimationItem` in `io.pythia.method.bucketsampled` (task-102). A `BucketedEstimationItem` belongs to a bucket (`bucketId`) and is either a **sample** — carrying its own `optimistic`/`likely`/`pessimistic` three-point estimate, from which `mean`/`variance`/`offerPT` derive by the usual PERT formula — or a **non-sample**, whose neutral values are the per-bucket average of that bucket's samples. Because a single leaf can't see its bucket siblings, the module overrides the SPI's `calculateAll(items, params)`: `computeBucketAverages(items, params)` averages each bucket's samples once, then `withCalculatedFromBucket(mean, variance, offerPT)` stamps those onto the non-sample leaves (`cost`/`offerPrice` derive from `offerPT` via the inherited getters). `EstimationVersion.calculate()` dispatches through this batch hook — it detects the method from the leaf types (any `BucketedEstimationItem` → `BUCKET_SAMPLED_PERT`, else `THREE_POINT_PERT`), runs `calculateAll` over the flat leaves, and substitutes the calculated leaves back into the tree by `logicalId` before the group accumulation; the PERT path stays byte-identical because its default `calculateAll` is per-leaf. This adds a `model → method` reference (`EstimationVersion` → `EstimationMethodRegistry`), which is acceptable (consistent with `DomainFactory`) and is NOT a method-to-method reference.
