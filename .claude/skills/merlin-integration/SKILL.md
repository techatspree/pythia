# Merlin Project integration

Two endpoints on `EstimationVersionResource`:

- `POST /api/estimations/{eid}/versions/import/merlin` — import a Merlin project WBS as a new draft version (multipart `file`; `409` if a draft already exists, `400` if the upload is unreadable).
- `POST /api/estimations/{eid}/versions/{n}/merge/merlin?overwriteStructure=` (operationId `mergeIntoMerlin`) — merge this version into an uploaded Merlin document and return the merged **copy** plus a report, as JSON `MerlinMergeResultDto` (multipart `file`; `409` + `MerlinStructureDiffDto` when the structure drifted, `400` if the upload is unreadable). Until task-223 this was an "export" endpoint returning the bare file; its old path is gone, not aliased.

## WBS import (task-131)

`MerlinImporter` (`io.pythia.service`, alongside `ExcelImporter`) turns a **Merlin Project** document's Work Breakdown Structure into a new draft version. A `.mproject` is a macOS bundle whose `state.sql` is a **SQLite 3 database** (an Apple Core Data store, `Z`-prefixed tables); activities live in `ZSCHEDULEITEM` (`ZTITLE`, `ZPARENTACTIVITY_` for hierarchy, `ZORDERINPARENTACTIVITY`, `ZISMILESTONE`, `ZGIVENWORK_` = a short string like `"1d"`). Activities are filtered by `ZTITLE IS NOT NULL` (resource-assignment rows have no title; **do not** gate on the version-specific `Z_ENT`).

The upload is accepted either as a **zipped** `.mproject` (the importer finds the `state.sql` entry) or the raw `state.sql`; it is read via a plain `org.xerial:sqlite-jdbc` `DriverManager` connection on a temp file — **not** a Quarkus datasource (the app DB stays PostgreSQL). Work maps to person-days (d×1, w×5, h×0.125) and a single value seeds optimistic=likely=pessimistic (the task's "single work → triple").

Output **preserves the WBS tree (groups + nesting) for both methods**; only the leaf type is method-specific (off `estimation.method`): `THREE_POINT_PERT` → `DraftFixedItemNode`, `BUCKET_SAMPLED_PERT` → `DraftBucketedItemNode` assigned to a single "Imported" bucket (`isSample` = has work). Buckets classify items; they do NOT replace the tree grouping. **Dependencies come along (task-221).** Merlin keeps them in `ZDEPENDENCY`: `ZPREVIOUSACTIVITY_` is the predecessor, `ZNEXTACTIVITY_` the successor (both a `ZSCHEDULEITEM.Z_PK`), `ZTYPE` the kind, `ZLAG_` an undecoded lag blob. Each row becomes a `DraftScheduleDependency` on the new draft, by the `logicalId`s of the nodes built for those activities; an edge may name a group or a leaf (task-164). Rules, all skips logged as one WARN per category and never fatal to the WBS import:
- **Only `ZTYPE = 0` is imported, as finish-to-start.** That mapping is an assumption from observed data (both rows of the demo file, Merlin's default type), not from a spec. Other types (start-to-start, finish-to-finish, start-to-finish) have no Pythia equivalent and are skipped.
- **A lag is dropped, the edge kept**: it still orders the two activities.
- **Unplaceable edges are skipped**: an endpoint that is no imported node (the project root activity, which is the estimation itself; a title-less assignment row; a dangling reference) or a self-edge.
- **Duplicates collapse** to one edge (first in `Z_PK` order), because the UNIQUE `(version_id, from_logical_id, to_logical_id)` constraint would otherwise abort the whole import.
- **No `ZDEPENDENCY` table** (an older or stripped document) means no edges, logged at DEBUG. Cycles are imported as they are; the domain reports them as `ScheduleError(CYCLE)`.

The demo file has two rows, Initialisation → Implementation and Implementation → Closure (top-level groups).

`EstimationVersionService.importMerlinDraft` guards "one draft at a time" (`409`) and does the version-numbering/persistence like `createDraft`; the frontend control is on the estimation detail page.

## Merge into Merlin (task-133, renamed from "export" in task-223)

`MerlinMerger` (same package) is the mirror of the importer — it merges the estimation into an EXISTING Merlin document the user uploads and keeps everything Pythia does not own (dates, resources, assignments, calendars). It **only ever edits a COPY**: the uploaded bytes go to a temp file and are modified there; the user's own `.mproject` is never touched (a zipped upload is repacked with only its `state.sql` entry swapped).

**The response is JSON, document and report in one** (`MerlinMergeResultDto`: `fileName` `merlin-<draft|vN>-merged.<zip|sql>`, `document` as standard padded base64, `report`), because the merge is stateless and a second request would mean a second upload. The body is about 4/3 of the file; the 32m/32M limits below apply to requests only. The frontend saves the file (`downloadBlob(base64ToBlob(…))` in `#lib/api/download.ts`) and then opens `MerlinMergeReportDialog.svelte`. The report (`MerlinMergeReport` → `MerlinMergeReportDto`) lists: efforts changed (path, before/after PT, null = no work), activities added/moved (the applied drift lists) and removed (`ObsoleteDeletion.activities`), dependencies removed with deleted activities, added and skipped (with a reason), and `contentRemoved` counts — `assignments` from `ObsoleteDeletion.assignments`, the rest from `removedRows` by table (`ZCOMMENT`, `ZATTACHMENT`, `ZCOST`, `ZCUSTOMATTRIBUTEVALUE`). Comment readings, view configurations and list-value joins are bookkeeping and not reported. The dialog renders the sections in a fixed order (structure first, efforts last), hides empty ones, and says "no changes" when everything is empty.

The value written is the calculated **`offerPT`** (mean + risk surcharge) of each **LEAF** — Merlin derives a parent's work from its children, so group activities are left alone — encoded into `ZGIVENWORK_` exactly as Merlin writes it: ASCII `"<days>d"` plus a trailing `0x3F` marker byte (`X'31643F'` is `"1d?"`), with `Z_OPT` bumped on every changed row and `NULL` written for a leaf with no effort. **Only changed leaves are written** (task-223): current and new value are compared as `formatDays` strings — the 2-decimal form the writer stores — after `parseWorkToPersonDays` on the current one, so merging a merged file again is a no-op. A numeric tolerance would sit exactly on `formatDays`' HALF_UP boundary.

**Dependencies are merged ADD-ONLY** (task-223, the user's decision). For each Pythia schedule edge whose endpoints map (logicalId → WBS path → activity pk, on the activities as they are after any overwrite) a finish-to-start `ZDEPENDENCY` row is INSERTed (`ZTYPE 0`, `ZLAG_` NULL, `Z49_*` = 49, `ZPROJECT` of the root activity, `Z_ENT` and pk from the `Z_PRIMARYKEY` row named `Dependency` — 24 in the demo file — whose `Z_MAX` advances). A Merlin dependency Pythia lacks is **never deleted**: the merge cannot tell "deleted in Pythia" from "added in Merlin". `DependencyMerge` checks, per edge: already present from → to (any type) → nothing; one end an ancestor of the other → skipped as `PARENT_CHILD` (a group's dates come from its own children); the successor already reaches the predecessor through the document's edges, including those added so far → skipped as `WOULD_CREATE_CYCLE`. Edges whose node is not in the version or has no activity are skipped silently. A document without `ZDEPENDENCY` or that `Z_PRIMARYKEY` row gets no edges (WARN).

The version is resolved by the resource's existing `resolveVersion(...)` helper, so `draft` and a submitted number both work and `MerlinMerger` consumes the same `SubmittedEstimationVersion` the xlsx/csv exporters take. The frontend picks that ref itself (`mergeVersionRef`): the draft while one exists, otherwise the **highest submitted version** — submitting CONSUMES the draft, so hardcoding `draft` would 404 exactly when the estimate is finished and you want it back in Merlin (the button is disabled when the offer has no version at all).

**Correlation is by WBS path** (titles joined with `" / "`), the only key the import leaves behind — so before writing anything the merger compares the ordered path lists of both sides and, on drift, throws `MerlinStructureChangedException` → `409` `MerlinStructureDiffDto` (`missingInMerlin` / `missingInEstimation` / `reordered`). The protocol is **stateless**: the frontend re-POSTs the same file with `?overwriteStructure=true` once the user confirms in `MerlinStructureDialog.svelte`.

That overwrite **reconciles by path** rather than wiping and rebuilding — activities that still exist keep their row (and their dates, dependencies and assignments), missing ones are INSERTed, and obsolete ones are DELETEd together with everything that refers to them (task-222), so the returned document holds no reference to a row that is gone. The cascade (`ObsoleteCascade` in `MerlinMerger.kt`) works from an **explicit, ordered list** of references, measured by scanning every column of the demo file. It is not discovered at runtime, because a scan would also delete through columns nobody checked. A table or column a document lacks (an older Merlin) is skipped, checked via `pragma_table_info`:
- **What goes.** The obsolete activities' **assignments** (`ZSCHEDULEITEM.ZACTIVITY_`) go first. From then on the cascade runs over activities AND assignments, since anything below may name either.
- **Content owned by a deleted item goes too, recursively:** comments (`ZCOMMENT`, with their `ZCOMMENTREADING`s) and attachments (`ZATTACHMENT`, with everything hanging off them). Ownership is **circular**: a comment may belong to an attachment (`ZCOMMENT.ZATTACHMENT`) and an attachment to a comment (`ZATTACHMENT.ZCOMMENT`). So both sets are collected until nothing new is found.
- **References with no content of their own** are deleted: `ZDEPENDENCY` (either end), `ZOBJECTVIEWCONFIGURATION` (`ZSCHEDULEITEM_`/`ZATTACHMENT_`), the list-value joins `Z_48ASSOCIATEDLISTVALUES`/`Z_1ASSOCIATEDLISTVALUES`, `ZCOST` and `ZCUSTOMATTRIBUTEVALUE` (each on an item or an attachment).
- **Order:** dependents first, then comments and attachments, then the schedule items.
- **Rank chain:** a KEPT activity's `ZRANKNEXTACTIVITY_`/`ZRANKPREVIOUSACTIVITY_` that pointed at a deleted one is set to NULL, together with its `Z49_` entity-type column, rather than cascaded.
- **NOT references despite their names:** `ZGIVENPERMISSIONFORACTIVITIES`/`ZGIVENPERMISSIONFORATTACHMENTS` on `ZRESOURCE` and `ZRESOURCEGROUP` are integer flags. `ZPROJECT.ZROOTACTIVITY` names the root, which is never obsolete. The `Z1_`/`Z48_`/`Z49_` columns beside a reference are Core Data's entity-type columns and go with their row.
- **Return value:** `deleteObsolete` returns an `ObsoleteDeletion` (deleted activity paths, removed dependencies as path pairs, rows per table, and the number of deleted assignments), which feeds the merge report.
- **Not verified in Merlin:** whether Merlin accepts the result is checked **manually** only (macOS app, not in CI).

The dialog text (`merlin.diffBody`) names dependencies, comments and attachments, so the user knows what "Struktur überschreiben" destroys. New rows take their `Z_PK` from the Core Data `Z_PRIMARYKEY` table using the row for **`Z_ENT = 48`** (`ScheduleItem`, the ROOT of the hierarchy `Activity`=49 and `Assignment`=51 inherit from — the subclass rows carry `Z_MAX = 0` and must not be used) and get a fresh 22-char URL-safe base64 `ZUNIQUEID`.

**A Merlin title may itself contain the `" / "` separator** (the sample has `"… Layer-2 / Layer-3"`), so a node's parent and title are captured during the tree walk and never recovered by splitting the path string — doing that reparents such activities to the root.

## Upload size is a GATEWAY concern, and it is cluster-only

Both Merlin endpoints POST a whole `.mproject` as multipart — real documents are several MB (even the committed `planning/inputdata/MerlinDemoProject.mproject/state.sql` is 1.5 MB). nginx' default `client_max_body_size` is **1m**, so in the cluster a normal-sized Merlin file was rejected with a bare `413` *before* being proxied: nothing reached the backend, nothing appeared in the backend log, and only `kubectl logs deploy/frontend` showed `client intended to send too large body`.

Local dev never reproduces it — the Vite dev proxy imposes no limit — and neither does the Playwright suite, which also goes through Vite; **no test covers the gateway config**. `src/frontend/nginx.conf` therefore sets `client_max_body_size 32m` on `location /api/`, matched by `quarkus.http.limits.max-body-size=32M` (Quarkus' own default is 10M). Keep the two numbers in sync: the smaller one is the effective limit, and raising only one just moves the rejection one hop. A change here lives in the frontend IMAGE, so it needs a rebuild + redeploy, not a `kubectl apply`.
