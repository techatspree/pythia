# Collaborative estimation sessions

Narrative overview for humans: `docs/estimation-sessions.md`. This file is the implementation detail.

## Persistence (V13 migration)

Four tables under `io.pythia.domain.session` (all JPA `BaseEntity` — uuid `id` + `created_at`/`updated_at`).

`estimation_sessions` (`EstimationSession`: `estimation_id` FK, `title`, `moderator_subject_id`, `status`, `current_item_index`, `current_phase`, `finalized_at`, and `moderator_estimates` boolean default true — V14, task-129: whether the moderator also votes). The coarse lifecycle is `SessionStatus` (`CREATED`/`RUNNING`/`SUSPENDED`/`FINALIZED`/`ENDED_EARLY`/`CANCELLED`); per-item progress is tracked by `session_items.status` + `current_item_index`/`current_phase`.

`SUSPENDED` and `ENDED_EARLY` are task-144: `CREATED → RUNNING → (SUSPENDED ⇄ RUNNING) → FINALIZED | ENDED_EARLY`, with `CANCELLED` as the abandon exit. The distinction is deliberate — **`ENDED_EARLY` keeps its results** (it is a session that ran out of time, and it sets `finalized_at` like a normal finish), while `CANCELLED` stays the "this session was a mistake" exit. Nothing needed a Flyway migration for the two new constants: `estimation_sessions.status` is a plain `VARCHAR(255)` with **no** check constraint, mapped `@Enumerated(STRING)`, so a new enum name persists as-is — do not add a migration that rewrites a constraint which does not exist. `EstimationSessionRepository.findJoinable()` lists `CREATED`/`RUNNING`/**`SUSPENDED`** (a parked room must stay discoverable or it can never be resumed) and excludes every terminal state.

`session_items` (`SessionItem`: `node_logical_id` — a **soft** reference to a draft leaf's `logical_id`, not an FK — `position`, `status` = `SessionItemStatus`, `discussion_notes`, and the `final_min/expected/max_effort` write-back triple; `UNIQUE(session_id, node_logical_id)`). `session_participants` (`SessionParticipant`: `subject_id`, `display_name`, `participant_role` = `ParticipantRole`, `agreed`; join time is `created_at`; `UNIQUE(session_id, subject_id)`). `session_votes` (`SessionVote`: `session_item_id` FK, `participant_subject_id`, `phase` = `SessionPhase`, the `min/expected/max_effort` triple; submission time is `created_at`; `UNIQUE(session_item_id, participant_subject_id, phase)` so a re-vote in a phase overwrites). All FKs cascade-delete from the session.

The vote/finalize columns are the **THREE_POINT_PERT** shape; `V17` (task-106) adds the bucket+sampled vote shape to `session_votes` — a nullable `bucket_id` (FK to `estimation_buckets`, `ON DELETE RESTRICT` so deleting a bucket a cast vote references fails loudly instead of rewriting session history) plus `is_sample`, mirroring the node tables' V10 columns; a sampling bucket vote reuses the existing `min/expected/max_effort` triple, and a PERT session leaves both new columns null. Both are declared on the `SessionVote` entity too, per the V15 entity/migration-parity lesson (see `src/backend/CLAUDE.md`).

Repositories: `EstimationSessionRepository` (`findByEstimationId`, `findParticipant`, `findJoinable`) and `SessionVoteRepository` (`findBySession`, `findByItemAndPhase`).

## REST control plane (`SessionResource`, task-064)

Base path `/api/sessions`, all `@RolesAllowed("ESTIMATOR")`; moderator-only actions additionally check the caller's subjectId equals the session's `moderator_subject_id` (→ `403`), and vote/phase state guards return `409`. Every mutation returns the full `SessionDto` and fires `SessionEventPublisher` (a CDI `Event<SessionChangedEvent>` the WebSocket layer observes).

`POST /api/sessions` (moderator = caller; body `{estimationId, title, itemLogicalIds, moderatorEstimates?}` — `moderatorEstimates` defaults true (task-129); when false the moderator only moderates and a vote from them is `409`; also exposed on `SessionDto.moderatorEstimates`; `400` if a logicalId is not a draft leaf), `GET /api/sessions/{id}`, `GET /api/sessions?estimationId=…` (the `estimationId` query param is **optional** — task-128; omit it to list all joinable CREATED/RUNNING/SUSPENDED sessions across every estimation, via `EstimationSessionService.listJoinableSessions()` / `EstimationSessionRepository.findJoinable()`, which powers the frontend's open-sessions join list), `POST …/{id}/join` (idempotent ESTIMATOR participant), `POST …/{id}/start` (CREATED→RUNNING), `PUT …/{id}/items/current/notes`, `POST …/{id}/items/current/phase2` (reveal), `POST …/{id}/items/current/finalize` (writes the aggregate mean triple back onto the draft leaf **through the draft-update path** so the change is undoable, and appends the item's discussion notes — prefixed with the session name — to that leaf's `assumptions` in the same write (task-129), then advances), `POST …/{id}/votes` (upsert the current-item current-phase vote), `POST …/{id}/votes/bucket` (task-106 — the BUCKET_SAMPLED_PERT vote: body `{bucketId, isSample?, minEffort?, expectedEffort?, maxEffort?}`, a separate payload rather than an overloaded `VoteRequest` because a bucket vote's required field is the bucket and its triple is optional; `409` when the estimation is not bucket+sampled or the bucket belongs to another estimation), `POST …/{id}/agree`, `POST …/{id}/cancel`.

Plus the three moderator-only lifecycle transitions of task-144 — `POST …/{id}/suspend` (RUNNING→SUSPENDED), `POST …/{id}/resume` (SUSPENDED→RUNNING), `POST …/{id}/end-early` (RUNNING or SUSPENDED→ENDED_EARLY, setting `finalizedAt`) — each `403` for a non-moderator and `409` from the wrong source state. A `SUSPENDED` session is **inert**: `submitVote` already refused a non-RUNNING session, and task-144 added the same explicit `RUNNING` guard to `revealPhase2` and `finalizeCurrent`, which previously checked only the item/phase state and so would have accepted a reveal or a finalize in a parked room (`join`/`agree` stay unguarded); the guard is the single `requireRunning(session, id)` helper rather than three copies of the same `if`, because inlining it a third time pushed `finalizeCurrent` over detekt's CyclomaticComplexMethod threshold. `endEarly` deliberately does **not** aggregate the in-flight item — every item finalized earlier was already written back to the draft leaf per item, so there is nothing to flush, and finalizing a partially-voted item would invent a number nobody agreed on; that item simply keeps no final triple.

During a blind PHASE1 an item exposes only `submittedVoteCount`; votes + the aggregate appear once the item is PHASE2/FINALIZED. Mean/spread/divergence is **never computed in the service** — since task-105 both reduction call sites (`finalizeCurrent` and the `itemDto` builder) dispatch through `EstimationMethodRegistry.requireSession(session.estimation.method).reduce(...)`, which for PERT delegates to the domain `VoteAggregation.aggregate(...)` (task-062). `itemDto` has no access to the estimation, so `buildDto` resolves the support **once per DTO build** and passes it down as a parameter. Since task-142 the SPI speaks `SessionVoteInput`/`SessionReduction`, so a single private `reducePert(support, votes)` helper does the `PertVoteInput` wrap and the `PertReduction` unwrap for both call sites. The frontend still calls the `aggregateVotes` bridge directly — the SPI and registry are domain-internal, so a JS-side dispatch would need a new `@JsExport` bridge.

## Realtime channel (`SessionSocket`, task-065)

A **push-only** WebSocket at `/ws/sessions/{sessionId}` (`quarkus-websockets-next`) broadcasts the fresh `SessionDto` to every joined connection whenever state changes — mutations still go **only** through the REST control plane. `SessionBroadcaster` observes task-064's `SessionChangedEvent` (`@Observes(during = AFTER_SUCCESS)`, so it pushes committed state without socket I/O inside the transaction) and sends the **same** payload to all connections (PHASE1 hiding is already uniform, so no per-recipient scoping). Server→client messages: `{type:"session", session: SessionDto}` on every change (and on connect), `{type:"error", message}` on a handshake problem.

**Browser auth:** browsers can't set an `Authorization` header on a WS handshake and auth is provider-specific, so a joined participant first `POST`s `/api/sessions/{id}/ws-ticket` (ESTIMATOR + participant → `403`/`404` otherwise) to mint a short-lived, single-use opaque ticket (`SessionTicketStore`, ~30s TTL), then opens `ws://…/ws/sessions/{id}?ticket=…`; `@OnOpen` consumes the ticket (matching sessionId), re-confirms participation, and otherwise closes with a policy-violation (1008).

**Reconnect re-syncs itself — do NOT add a REST re-fetch to that path.** `@OnOpen` calls `broadcaster.sendSnapshot(...)`, so every successful (re)connect immediately receives the current `SessionDto`. State lost during a disconnect heals on reconnect; the hard part was never fetching, it was *noticing* the disconnect.

**Heartbeat + watchdog (task-147).** The client cannot tell a quiet room from a dead socket on its own: JS can neither send WebSocket protocol pings nor observe pongs, and a healthy room legitimately sends no frames for minutes. So `SessionBroadcaster.heartbeat()` (`@Scheduled(every = "{app.session.heartbeat-interval}")`, 20s in prod, 1s in `%test`) pushes `{"type":"heartbeat"}` to every open connection, and `socket.ts` treats **any** received frame as proof of life, resetting a 45s idle watchdog (> 2 beats, so one lost frame is not a false positive). On expiry it tears the socket down itself and reopens with `attempt` reset — a silent death (sleep, NAT/proxy idle-kill, a broken path that never fires `onclose`) would otherwise leave the room stale forever. `quarkus.websockets-next.server.auto-ping-interval=30s` is the server-side mirror that reaps vanished clients; deliberately NOT paired with `connection-idle-timeout`, which the heartbeat would keep from ever firing except on healthy rooms.

**The socket is the only writer of live session state (task-160).** A mutation's REST response used to be applied straight to the store as well ("snappy feedback"), in the room page and both phase panels. That DTO is built INSIDE the mutation's own transaction, so it is blind to anything a concurrent participant committed — a second, unordered writer into the slot the socket owns. OBSERVED (reproduced 1 run in 15 of the full e2e suite, with the backend log, the Playwright trace and the DB row kept): an estimator's `POST /votes` and the moderator's `POST /end-early` overlapped; both broadcasts went out `to 2 connection(s)`, the estimator's socket never closed or reconnected and its indicator stayed green, the DB read `ENDED_EARLY` — and the estimator's room showed `RUNNING` with one vote on item 2, i.e. exactly its own vote response, applied after the end-early frame. Nothing else changes in an ended session, so the room stayed stale indefinitely; the moderator survived only because its last write happened to be the correct one. The heartbeat/watchdog pair below was NOT involved and is unchanged. Mutations now `await` their call for its errors and let the broadcast update the store; only the socket's `onSession` and the room's pre-connect initial load may call `SessionStore.apply`. `e2e/session.test.ts` pins it by ending the session while the estimator's vote is deliberately still in flight and re-asserting after that response lands.

**`connected` comes from the socket, never from a payload.** `SessionStore.setConnected(...)` is driven by `connectSessionSocket`'s `onConnectionChange` (open → true; close/error/watchdog → false). It used to be set inside `apply(session)` — liveness inferred from "a message arrived once", which can never become false again, so the room's green dot stayed green over a dead socket and told the user stale data was live. Do not reintroduce that. `ws.onerror` reports disconnected but must NOT schedule a reconnect: the browser fires `onclose` afterwards, and scheduling in both doubles the backoff per failure. `e2e/session-connection.test.ts` pins both directions of the indicator.

## Frontend (task-066/067)

A route group under `src/frontend/src/routes/sessions/`. It used to be a **separated** group with its own room chrome while the root header was hidden for `/sessions` — that made the room look unlike the rest of the app and left no recognisable way back, so task-141 deleted it, and task-148 finished the job: `sessions/+layout.svelte` is now a bare pass-through with no chrome AND no background, because the session pages use the same visual system as every other route — white surface, full-width `p-6` wrapper (never `max-w-* mx-auto` on the page; constrain an inner block instead, as the setup form does), and the shared bordered-card idiom `border rounded-lg overflow-hidden` + a `bg-brand-green/10 text-brand-green text-xs font-semibold uppercase tracking-wide` header strip + a `p-4` body, exactly as `ParametersPanel` and its three siblings. Two traps remain if you try to make the room fill the viewport: do NOT put `min-h-screen` on the layout — stacked under the global header it pushes every session page past the fold and leaves a permanent scrollbar over dead space; and do NOT make the root `<main>` a flex container so the wrapper can `flex-1` — that turns every page's root element into a flex item, whose automatic minimum size stops the TreeTable's horizontal scroll wrapper from overflowing, which `e2e/treetable-responsive.test.ts` catches (`h-full` does not resolve there either). The room page carries a contextual `session.room.backToEstimation` link (visible in every session state, unlike `SessionSummary`'s own back link which only appears once FINALIZED).

`sessions/+page.svelte` is the moderator setup (pick project → offer, flatten the draft's leaves into a checkbox picker, name + create → navigate to the room); it is also launchable **directly from the active offer** — the estimation detail page's "Start estimation session" button links to `/sessions?estimationId=&projectId=`, which pre-scopes the picker (task-128). That picker default-selects only the **not-yet-estimated** leaves (PERT triple all null-or-0), badges the already-estimated ones, and offers select-all/deselect-all; an **open-sessions** list at the top (from `listJoinableSessions()`) lets anyone discover and join a running or paused session. The dev `TestDataSeeder` seeds a "U05: Noch zu schätzen" group of 0/0/0 leaves on the Webshop draft so the unestimated preselect is demonstrable.

`sessions/[id]/+page.svelte` is the room page. The client lives in `$lib/session/`: `api.ts` (typed `apiFetch` wrappers over every `/api/sessions` endpoint incl. `getWsTicket`), `socket.ts` (`connectSessionSocket` — fetches a ws-ticket, opens `ws(s)://…/ws/sessions/{id}?ticket=…`, parses `{type:"session"|"error"}` frames, auto-reconnects with backoff re-fetching a ticket each attempt, `close()` disposer; failures both `log.error` and surface via `ErrorBanner`), and `store.svelte.ts` (`SessionStore` runes class holding the pushed `SessionDto` with `isModerator`/`currentItem`/`myParticipant`/`submittedCount` getters). The gateway proxies WS upgrades: vite dev `'/ws': { ws: true }`, and an nginx `location /ws/` upgrade block mirroring `/api/`.

### Two-phase flow (task-067)

The room page picks a panel from `store.session.status`/`currentPhase` and mounts one of three components under `$lib/session/`. On mount an estimator auto-joins (idempotent — a `SUSPENDED` room counts as joinable) and, once CREATED, the moderator starts the session.

`PhaseOnePanel.svelte` — every participant (the moderator estimates too) submits a **blind** PERT triple (only the submitted/total count is ever shown, never others' numbers); the moderator additionally edits the shared discussion notes (debounced PUT) and reveals PHASE2. `PhaseTwoPanel.svelte` — reveals the votes table + the aggregate (mean triple, PERT mean, and the spread: range / std-dev / coefficient of variation), with an amber highlight when `diverged`; estimators may submit a revised triple + toggle "I agree"; the moderator finalizes.

The mean/spread is **never** hand-rolled in the component — it is computed by the domain `VoteAggregation` (task-062) reached through the JS-friendly `aggregateVotes(Array<EstimatorVote>)` factory in `DomainFactory.kt` (the same Kotlin/JS-bundle pattern `adapter.ts` uses), so it is the single source of truth and matches the backend `AggregateDto` byte-for-byte (asserted in `e2e/session.test.ts`).

`SessionSummary.svelte` renders the FINALIZED per-item final triples + a link back to the estimation (finalize wrote those values onto the draft leaves through the draft-update path, so they are undoable) — and task-144 renders the **same** component for an `ENDED_EARLY` session above a short "ended early" note, rather than a second summary component: it already handles an item with no final estimate (`session.summary.noFinal`), which is exactly the shape of a session that stopped short. **The room's status branching is a chain whose trailing `{:else}` IS the RUNNING case, so a new status branch must be inserted before it or it silently renders the running panel.**

All numeric display goes through `$lib/format.ts`; all strings through the `session.*` i18n keys; every error path both `log.error`s and surfaces via `ErrorBanner`.
